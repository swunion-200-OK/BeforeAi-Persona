## 2. MBTI와 성향

### 2.1 INTP 특징이 드러나는 모습

- **내향(I)**: 전체 회의보다 슬랙 스레드에서 길게 씀. 말로 할 때는 생각을 다 정리하지 않은 채 꺼내서 말이 중간에 끊김
- **직관(N)**: 사고가 나면 "이번 건"보다 "같은 구멍이 몇 개 더 있나"를 먼저 셈. 사고 다음 날 42곳 고객사 운영 DB 접속 정보를 전부 목록으로 뽑음
- **사고(T)**: 업체 데모에서 화면보다 오류 코드 표를 먼저 봄. "실패할 때 뭐라고 하는지가 제품의 진짜 모습"
- **인식(P)**: 일정은 느슨하게 잡고 마지막 이틀에 몰아서 끝냄. 노현숙 팀장이 마감일을 하루 앞당겨 알려 주는 걸 알고 있음

### 2.2 MBTI를 대하는 태도

- 재미로는 봄. 슬랙 프로필에는 적지 않음
- 노현숙 팀장이 ISFJ라는 걸 듣고 "그래서 숫자를 끝까지 맞추시는구나" 하고 이해함
- "MBTI보다 그 사람이 장애 났을 때 뭘 하는지가 더 정확하다"는 입장

### 2.3 성격 요약

| 강점 | 약점 |
| --- | --- |
| 원인을 끝까지 팜. 사고 회고 문서를 가장 길고 정확하게 씀 | 설명이 길고 결론이 늦게 나옴. 비개발자는 중간에 놓침 |
| 손이 빠름. 급한 수정은 직접 해서 30분 안에 끝냄 | 일을 남에게 맡기지 않고 직접 해서 본인이 병목이 됨 |
| 비용 감각이 있는 편. 클라우드 예약 인스턴스로 월 60만 원 줄인 적 있음 | 사람 시간 비용은 잘 계산하지 않음. "제가 하면 되죠"가 입버릇 |
| 정직함. 본인 실수도 회고 문서에 그대로 씀 | 남의 실수도 그대로 써서 팀원이 상처받을 때가 있음 |
| 새 기술을 빨리 익힘. AI 코딩 도구를 회사에 처음 들임 | 새 도구에 대한 기대가 커서 위험을 늦게 봄. 이번 사고가 그 대가라고 생각함 |

### 2.4 스트레스 반응

- 사고가 나면 말이 줄고 터미널만 봄. 끝나고 나서야 슬랙에 긴 정리 글을 올림
- 잠을 줄여서 버팀. 사고 주간에는 하루 4시간 잤음
- 풀 때는 밤에 한강 자전거를 1시간 탐. 아내는 "또 탄다"고 걱정함

### 2.5 의사결정 스타일

1. 실패 경로부터 본다 ("이게 틀렸을 때 뭐가 멈추고, 누가 알게 되나")
2. 직접 만들 수 있는지 계산한다. 대개 "만들 수는 있다, 유지할 사람이 없다"로 끝남
3. 무료 대안을 먼저 써 본다. 써 보고 안 되는 이유를 적어 둠
4. 사람 한 명이 빠져도 돌아가는지 본다. 28명 회사라 이게 가장 자주 깨짐
5. 결정은 노현숙 팀장의 숫자와 대표의 "돈 써도 돼"가 같이 있어야 끝난다는 걸 앎

- 대학 때 쇼핑몰 아르바이트로 상품 등록과 주문 처리를 해 봄. 주문 상태가 꼬이면 고객 전화가 얼마나 오는지 이때 처음 앎
- 군대(공군 전산병) 시절 서버실 출입 기록 관리를 맡았음. "기록이 없으면 아무도 책임지지 않는다"는 걸 배움

### 4.3 기억에 남는 성공과 실패

**성공: 2023년 다온예약 결제 이중 청구 방지**
- 결제 대행사 응답이 늦을 때 같은 예약이 두 번 결제되는 문제를 멱등 키(같은 요청을 두 번 처리하지 않게 하는 키)로 막음
- 이중 청구 민원이 월 평균 14건에서 0건이 됨
- 이 경험 때문에 본 서비스의 nonce 1회 소진(명세 2.4, 5.1)을 보자마자 "이건 제대로 만들었다"고 판단함

**실패: 2026년 10월 14일(수) 숲결리빙 주문 상태 사고**
- 신동욱 개발자가 AI 코딩 에이전트에게 배송 상태 동기화 오류 수정을 맡김
- 에이전트가 노트북 `.env`에 있던 운영 DB 쓰기 계정으로 `UPDATE` 쿼리를 직접 실행. 날짜 조건이 빠져 주문 312건이 "배송완료"로 바뀜
- 87건은 고객에게 잘못된 알림톡이 나감. 복구는 10월 15일(목) 새벽 2시에 끝남 (4명, 약 9시간)
- 승재는 회고 문서에 근본 원인을 "운영 DB 쓰기 계정이 개발자 노트북에 있었다. 2019년에 내가 편하자고 만든 구조다"라고 적음
- 사고 비용은 노현숙 팀장이 약 340만 원으로 정리함 (유지보수비 감면 180만 원, 쿠폰 분담 62만 원, 야근 인건비 약 98만 원)

**아쉬움: 2020년 배포 스크립트 실수**
- 고객사 한 곳의 배포 스크립트가 다른 고객사 서버를 가리켜 이미지 캐시가 전부 지워짐
- 1시간 만에 복구했지만, 그 뒤로 배포 스크립트에 대상 서버 이름을 출력하고 확인하는 단계를 넣음

## 10. 본 서비스 도입 검토

### 10.1 승재가 정의한 문제

- 고객사 운영 DB에 쓰는 작업과 배포는, 사람이 내용을 보고 서명한 것만 실행되어야 한다
- 그 확인이 승재 한 사람의 눈에 의존하면 안 된다. 승재가 휴가여도 규칙은 동작해야 한다
- 고객사가 "누가 승인했냐"고 물으면 기록으로 답할 수 있어야 한다
- 이 모든 걸 인프라 담당 없이 운영할 수 있어야 한다

### 10.2 선택지 비교 (승재가 정리한 표)

| 선택지 | 첫해 비용 (현숙 팀장 계산 포함) | 막을 수 있는 것 | 못 막는 것 |
| --- | --- | --- | --- |
| 본 서비스 | 약 477만 원 (계정 14개, 서버 1대, 설치 지원) | 운영 DB 쓰기·배포·코드 수정 모두 서명 후 실행. 웹 서비스가 털려도 실행기가 해시를 직접 검증 | AI 분석 중 코드가 어디로 가는지는 아직 모름 |
| 현행 보강 (계정 분리 + 승재 확인) | 현금 0원, 승재 시간 월 약 33시간 | 승재가 볼 때만 막음 | 승재 부재 시, 승재가 실수할 때, 기록이 슬랙 메시지뿐 |
| 무료 DB 변경 승인 도구 자체 설치 | 서버 월 약 5만 원, 설치 3~5일 | DB 쓰기 쿼리 승인 | 배포, 코드 변경, AI 에이전트 실행 경로. 고객사 42곳 DB를 다 붙이는 데 시간이 많이 듦 |
| 직접 만들기 | 승재 약 2개월 (기회비용 큼) | 원하는 만큼 | 만든 사람이 승재라 결국 승재가 단일 장애 지점 |

### 10.3 승재가 명세를 읽고 좋게 본 점

| 기능 | 명세 근거 | 승재가 좋게 본 이유 |
| --- | --- | --- |
| 실행기가 Plan 해시를 직접 만들고 웹 서비스가 보낸 해시를 쓰지 않음 | 2.3, 5장 첫머리 | 숲결리빙 사고처럼 "Plan에 없던 쿼리"가 실행될 수 없음. 웹 서비스가 털려도 마찬가지 |
| 승인자 기기에서 Ed25519 서명 후 실행기 공개키로 HPKE 암호화 | 2.4, 4.5 | 웹 서비스는 envelope을 열어 보지 않고 전달만 함. 중간 바꿔치기 불가 |
| 실행기 검증 6단계, 하나라도 실패하면 웹쉘을 열지 않음 | 5.1 | 실패 원인이 `failedChecks`로 구분됨 (`PLAN_HASH_MISMATCH`, `NONCE_ALREADY_USED`, `MISSING_REQUIRED_APPROVER` 등) |
| nonce 1회 소진 | 2.4, 5.1 | 다온예약 이중 결제 방지와 같은 원리. 같은 승인으로 두 번 실행되지 않음 |
| DATA_WRITE·DB·DEPLOY 기본 위험도 HIGH | 1.3 | 숲결리빙 사고 쿼리는 DATA_WRITE라 HIGH로 분류됨 |
| 킬 스위치는 서명 없이, 외부망에서도 동작 | 4.6, 3.2 `POST /admin/kill-all` | 당번이 집에서 바로 멈출 수 있음 |
| 외부망에서는 CODE_MINOR·CODE_FEATURE만 승인 | 3.6, 4.4 `blockedReason: INTERNAL_NETWORK_ONLY` | 재택 중 실수로 운영 DB 승인이 나가지 않음 |
| 웹 코드 에디터도 승인·서명을 거침 | 3.8, 4.7 | 에디터로 몰래 고치는 길이 없음 |
| 금지 규칙 해제는 실행기 로컬 콘솔에서만 | 3.4, 5장 `RELEASE_PENDING_LOCAL` | 웹에서 누가 금지를 풀어도 실제로는 안 풀림 |
| 상태를 바꾸는 모든 API에 감사 로그 자동 기록 | 1.1, 4.8 | 숲결리빙 대책서에 "누가 언제 승인했는지 남는다"고 쓸 수 있음 |
| 실행기 연결 실패 시 상태 그대로 | 4.3 `502 EXECUTOR_UNAVAILABLE` | 연결이 끊겨도 "승인 없이 실행"으로 넘어가지 않음 |

### 10.4 승재가 걱정하는 점

| 걱정 | 명세 기준 상황 | 승재의 질문 |
| --- | --- | --- |
| 담당자 2명 이상 | 3.3 `POST /admin/projects`, `PUT /projects/{projectId}/owners`, 1.2 `409 OWNER_MINIMUM` | 고객사 42곳 대부분 담당 1명. 두 번째 담당을 다 승재로 적으면 HIGH 승인이 다시 승재에게 몰리지 않나 |
| 같은 부서 다른 사람 승인 | 2.2 `requiredApprovers.rule: SAME_DEPT_OTHER` | 다온예약 셀 4명 중 DB를 아는 사람은 류지아 1명. 내용을 모르는 사람이 서명하면 서명이 의미가 있나 |
| `SMALL` 프리셋 내용 | 3.2 `PUT /admin/policy/preset` (`SMALL` \| `MEDIUM` \| `LARGE`), 2.2 "규모별 정책(기능 명세서 5.5)" | 이 명세에는 `SMALL`이 어떤 규칙을 붙이는지 없음. 본인 승인이 어디까지 되는지 알아야 함 |
| 실행기 1대 운영 | 5장, 1.1 "Tailscale 내부망, mTLS" | 인프라 담당이 없음. 클라우드 1대에 Tailscale을 올리면 장애·패치·인증서 갱신은 결국 승재 일 |
| 실행기에 고객사 42곳 접속 정보 집중 | 5장 (실행기가 웹쉘 세션을 열어 실행) | 처제 말대로 실행기 한 대가 털리면 고객사 DB 접속 정보가 다 털림. 접속 정보 보관 방식 자료가 필요 |
| 웹 서비스 위치 | 1.1 "웹 서비스 서버만 실행기 API 호출 (mTLS)" | 웹 서비스가 업체 SaaS면 업체 서버가 우리 tailnet에 들어오는 건가. 우리가 설치하는 건가 |
| 망 판별과 Tailscale | 1.1 "Tailscale 100.64.0.0/10·회사 대역 = 내부망" | 재택 때 Tailscale 켜면 내부망이 됨. 그러면 외부망 제한이 사실상 없어지는데, 작은 회사는 이게 맞는지 |
| 프로젝트와 저장소 | 2.2 Plan의 `repository` 단일 값, 3.3 프로젝트 생성 | 고객사 한 곳에 저장소가 2개(쇼핑몰 프론트, 관리자)인 곳이 5곳. 프로젝트를 둘로 나눠야 하나 |
| 프로젝트 47개 등록 | 3.3 `POST /admin/projects` (ADMIN, 내부망) | 한 번에 등록하는 방법이 없음. 47번 손으로 해야 함 |
| DB 작업 되돌리기 | 3.7 `POST /requests/{requestId}/rollback`은 문서 작업만, 그 외 `400 VALIDATION_ERROR` | 숲결리빙 같은 DATA_WRITE 실수는 롤백이 없음. 승인으로 막는 것뿐 |
| Plan 수정 시 전체 재승인 | 4.2 `PENDING_APPROVAL`에서 수정 시 `REAPPROVAL_REQUIRED`, 기존 서명 모두 무효 | 쿼리 조건 하나 고쳐도 다시 다 받아야 함. 다만 숲결리빙 사고를 생각하면 이게 맞다고도 봄 |
| 분석 재시도 3회 | 3.5 `POST /requests/{requestId}/analysis/retry`, `409 RETRY_LIMIT` | 고객사 요청이 애매하면 3회를 금방 씀 |
| 킬 스위치 범위 | 4.6 `RUNNING`에서만 가능 | 이미 끝난 쿼리는 못 멈춤. 쿼리 한 줄이면 킬 스위치보다 승인이 더 중요 |
| 감사 로그 내려받기 없음 | 3.9 `GET /audit-logs`는 검색만 | 노현숙 팀장과 숲결리빙 보고에 필요 |
| 전체 감사 로그는 ADMIN만 | 3.9 권한 열 | 노현숙 팀장에게 ADMIN을 주면 승인 기준표(`PUT /admin/approval-matrix`)까지 바꿀 수 있음. 조회 전용 역할이 없음 |
| AI 분석 데이터 흐름 | 명세에 없음 (4.1 분석 단계 설명뿐) | 고객사 소스코드와 주문 데이터 샘플이 업체 AI로 가는지. 고객사 비밀유지 조항 위반 여부 |
| 승인 키 등록 | 3.1 `POST /me/signing-keys`, 3.2 `POST /admin/signing-keys/{keyId}/register` (관리자 서명 필요) | ADMIN이 승재 1명이면 키 등록도 승재가 병목 |

### 10.5 승재가 생각한 시범 계획 (회의 전 초안)

| 단계 | 내용 | 측정 지표 |
| --- | --- | --- |
| 준비 | 실행기 클라우드 1대, Tailscale, 키 등록 (승재 혼자 1.5일 목표) | 설치 시간, 막힌 지점 |
| 1주 | 숲결리빙, 다온예약, 공통 모듈 1개 등 프로젝트 3개, 개발자 5명 | 작업 유형 분포, 승인 대기 중앙값 |
| 2주 | 일부러 깨 보기: Plan 변조, envelope 재전송, 외부망 DEPLOY 승인, 실행 중 킬 스위치, 실행기 중지 후 제출 | `PLAN_HASH_MISMATCH`, `NONCE_ALREADY_USED`, `403 INTERNAL_NETWORK_ONLY`, `KILLED`, `502 EXECUTOR_UNAVAILABLE` |
| 종료 | 승재가 직접 확인한 운영 작업 건수 비교 (하루 9건 → 몇 건) | 승재 확인 시간, 승인자 분포 |

- 11월 4일 회의 뒤 바뀐 점 (`meeting-01-adoption-review.md`): 업체 데이터 처리 답변 전에는 고객사 코드를 넣지 않기로 해서 시범 프로젝트를 다온예약 저장소 2개와 공통 모듈 1개로 바꿈. 숲결리빙은 11월 18일(수)까지 서면 동의가 오면 11월 23일(월)부터 추가. 참여자는 승재, 하준영, 류지아, 남궁혁, 신동욱과 노현숙 팀장 계정 1개. 통과 표본은 실제 HIGH 완료 20건 이상, 승재 미참여 10건 이상, 승재 부재일 2일 이상

### 10.6 성공 기준

- 시범 프로젝트의 운영 DB 쓰기·배포 100%가 서명 후 실행
- 승재가 승인한 HIGH 작업 비율 50% 이하 (나머지는 다른 담당이 승인)
- LOW 작업 요청부터 실행까지 중앙값 10분 이내
- 실행기 운영에 쓰는 승재 시간 주 1시간 이내

## 11. 고민과 불안

- **본인이 병목**: 사고 후 하루 9건을 직접 보고 있음. 도구를 사도 승인이 다 승재에게 오면 의미가 없음
- **출산휴가**: 2027년 3월 2주 동안 승재 없이 운영 승인이 돌아가야 함
- **인프라 인력 없음**: 실행기 서버가 승재의 새 숙제가 될까 걱정. 서버 패치, 인증서, Tailscale 키 만료를 챙길 사람이 승재뿐
- **고객사 신뢰**: 숲결리빙 박지선 실장의 "다음엔 계약 다시 생각" 발언이 계속 떠오름
- **비용 설득**: 노현숙 팀장의 "공짜로 하는 방법은 없어요?" 질문에 "있지만 제 시간이 들어요"라고 답해야 하는데, 본인 시간을 돈으로 말하는 게 어색함
- **죄책감**: 사고 원인이 본인이 만든 `.env` 구조라는 것

## 12. 동기와 기대

- 운영 확인을 승재 한 사람의 눈에서 서명과 기록으로 옮기는 것
- 승재가 하루 1시간 30분을 다시 코딩과 고객사 기술 검토에 쓰는 것
- 신동욱 개발자가 다시 운영 작업을 겁내지 않게 하는 것
- 숲결리빙과 다른 고객사에 "AI가 운영에 닿는 작업은 담당자 서명 없이 실행되지 않습니다"라고 말할 수 있는 것
- 출산휴가를 마음 편히 쓰는 것

## 13. 커뮤니케이션 방식

### 13.1 업체를 대할 때

- 첫 미팅에서 가격표와 오류 코드 표를 같이 요청함
- "다음 버전에 됩니다"에는 "그럼 지금은 뭘로 대신해요?"라고 되물음
- 기술 담당과 직접 슬랙이나 메일로 대화하길 원함
- 보안 설명에서 틀린 말을 들으면 그 업체를 다시 보지 않음

### 13.2 팀원과

- 지시보다 질문으로 말함. "이거 틀리면 뭐가 멈춰?"
- 사고 회고는 사람 이름 대신 경로로 씀
- 팀원 불만은 1:1에서 듣고, 결정은 슬랙에 이유와 함께 남김

### 13.3 노현숙 팀장과의 관계

- 2021년 클라우드 결제 실패 사고 때 현숙 팀장이 밤 11시까지 남아 카드사와 통화하고, 승재는 고객사에 전화를 돌림. 그 뒤로 서로를 믿음
- 승재가 기술 설명을 길게 하면 현숙 팀장이 "그래서 한 달에 얼마예요?"로 끊음. 처음엔 서운했는데 지금은 그 질문이 결론을 앞당긴다는 걸 앎
- 현숙 팀장에게 설명할 때는 비유를 씀. "Plan 해시는 계약서 간인", "실행기는 금고, 서명은 열쇠"
- 현숙 팀장이 사고 비용 340만 원과 승재 시간 월 132만 원 상당을 표로 만들어 대표에게 보고한 뒤, 승재는 "현숙 팀장님 숫자가 제 설명보다 세다"고 말함
- 현숙 팀장이 무료 대안을 계속 물으면 귀찮기도 하지만, 그 질문 덕에 무료 도구를 실제로 써 보고 한계를 적어 둠

### 13.4 자주 하는 말

- "이거 틀리면 뭐가 멈춰요?"
- "제가 하면 되긴 하는데요."
- "만들 수는 있어요. 유지할 사람이 없어요."
- "그건 사람 문제 아니고 경로 문제예요."
- "그 오류 코드 명세 몇 절에 있어요?"

## 14. 반대로 돌아설 수 있는 사유

- 시범에서 HIGH 승인이 결국 승재에게 80% 넘게 몰리는 경우
- 실행기 설치·운영에 승재 시간이 주 3시간 넘게 드는 경우
- AI 분석 단계에서 고객사 소스코드나 운영 데이터가 업체 밖 제3자에게 가는데, 끌 방법이 없는 경우
- 웹 서비스가 envelope을 열 수 있거나, 실행기가 웹 서비스 해시를 그대로 쓰는 게 드러나는 경우
- 명세의 오류 코드와 실제 응답이 다른 경우 (예: 외부망 DEPLOY 승인이 `403 INTERNAL_NETWORK_ONLY`가 아닌 다른 코드로 옴)
- 업체 기술 담당과 직접 연락할 창구가 없는 경우

## 15. 사용 시나리오

### 시나리오 1: 숲결리빙 사고 다시 해 보기

1. 시범 환경에서 사고 당시와 같은 프롬프트("배송 상태 동기화 오류 고쳐줘")를 숲결리빙 시범 프로젝트에 `POST /requests`로 넣음
2. AI가 만든 Plan에 DATA_WRITE 작업(`content.query`)이 들어가고 위험도 HIGH로 분류되는지 봄
3. 쿼리에 날짜 조건이 빠진 것을 승인 화면(`GET /requests/{requestId}/approval-context`)에서 발견하고 `POST /requests/{requestId}/rejections`로 거부, 사유 "날짜 조건 없음"
4. 감사 로그(`GET /audit-logs?requestId=...`)에 `REJECTED`가 남는 것을 캡처해 고은비 PM에게 대책서 자료로 넘김

### 시나리오 2: 일부러 깨 보기

1. 시범 2주차, 웹 서비스 쪽 Plan의 쿼리를 바꾼 뒤 실행을 요청함
2. 실행기가 `403 VERIFICATION_FAILED`, `failedChecks: ["PLAN_HASH_MISMATCH"]`로 거부하고 Slack 경보가 오는지 확인
3. 같은 envelope을 다시 보내 `NONCE_ALREADY_USED`를 확인
4. 실행기를 멈춘 채 `POST /requests/{requestId}/submit`을 호출해 `502 EXECUTOR_UNAVAILABLE`이 나고 상태가 그대로인지 확인

### 시나리오 3: 새벽 당번

1. 새벽 2시, 남궁혁 개발자가 다온예약 예약 중복 데이터 정리 쿼리가 필요함
2. 집에서 Tailscale 없이 접속하면 DATA_WRITE 승인이 `blockedReason: INTERNAL_NETWORK_ONLY`로 막힘
3. Tailscale을 켜면 내부망으로 판별되어 담당자에게 승인 요청이 감
4. 승재는 이 시나리오를 보고 "Tailscale을 켜면 제한이 사라지는 게 맞나"를 업체에 물어보기로 함

### 시나리오 4: 승재 출산휴가

1. 2027년 3월, 승재가 2주 휴가를 앞둠
2. 하준영 리드를 커머스 프로젝트 담당에, 류지아 리드를 다온예약 담당에 두는 걸 `PUT /projects/{projectId}/owners`로 미리 바꿈
3. 승재를 담당에서 빼면 승재 서명이 필요한 승인 대기 요청이 `REAPPROVAL_REQUIRED`가 된다는 걸 알고, 휴가 3일 전에 바꾸고 대기 요청을 비움
4. 노현숙 팀장이 휴가 기간 감사 로그를 확인할 수 있게 조회 권한 문제를 미리 해결해야 함

### 시나리오 5: 무료 대안과 나란히 비교

1. 노현숙 팀장의 요청으로 무료 DB 변경 승인 도구를 시범 서버에 설치해 봄 (승재 1일)
2. 숲결리빙 DB 쿼리 승인은 되지만, 배포 스크립트와 AI 에이전트의 터미널 실행은 막지 못함을 표로 정리
3. 현숙 팀장에게 "무료 도구는 DB 문 하나만 잠그고, 본 서비스는 운영으로 가는 문을 다 잠근다"고 설명

## 17. 한 줄 요약

권승재는 **본인이 병목이라는 걸 아는** CTO입니다. 본 서비스가 서명과 실행기 검증으로 "승재가 안 봐도 승인 없는 운영 작업은 돌지 않는다"를 보여 주고, 28명 회사의 담당자 규칙과 실행기 운영을 승재 혼자 떠안지 않게 해 주면 가장 먼저 도입을 밀어붙이는 사람이 됩니다.
