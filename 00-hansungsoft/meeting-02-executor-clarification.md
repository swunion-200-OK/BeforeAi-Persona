## 1. 결정 사항

### 1.1 업체 보완 설명 요지 (업체 기술 담당 회신, 3주차 월·화요일 수령)

| 번호 | 보완 설명 | 당사 수용 여부 |
| --- | --- | --- |
| 1 | 실행기는 운영 작업을 대신 돌리는 별도 인프라 러너가 아니라, (a) Plan 해시 자체 생성과 Ed25519 서명·nonce를 검증하는 "서명 검증기", (b) 승인 envelope을 실행기 공개키로만 복호화하는 E2EE 종단, (c) 검증 6단계 통과 후 로컬에서 웹쉘 세션을 열어 작업을 수행하는 컴포넌트임 | 수용. 단, 시범 때 실제 동작으로 재확인 |
| 2 | 따라서 "전산실에 두는 무거운 서버, 대수 산정, 랙 공간" 식 우려는 상당 부분 과장이었음 | 조건부 수용 (아래 1.3) |
| 3 | 가용성(단일 컴포넌트 장애 시 실행 정지) 우려는 여전히 유효함. 이중화는 "서버 증설"이 아니라 "컴포넌트 다중화·페일오버" 관점으로 봐야 함 | 수용. 재서술 (아래 1.3) |
| 4 | 명세의 Tailscale은 개발·테스트 단계 임시 구성이며, 실제 운영 배포는 고객사 내부망 연결(웹 서비스↔실행기 mTLS, 내부망 대역은 관리자가 설정)로 이루어짐 | 수용. 배포 전제를 내부망 mTLS로 변경 (아래 1.4) |

### 1.2 보완 설명으로 내려간 우려 (1차 공문 5항 다. 대비)

| 1차 우려 번호 | 내용 | 재평가 결과 |
| --- | --- | --- |
| 5 | 실행기 단일 구성·이중화 방안 없음 | **등급 하향**. "서버 2대 증설"에서 "컴포넌트 다중화·페일오버"로 재서술. 우려 자체는 유지하되 비용·설치 부담 전제는 축소 |
| 3 | 야간·주말 외부망에서 Tailscale 접속 시 내부망 판별 여부 | **대부분 해소**. 배포는 내부망 mTLS 전제이므로 "Tailscale 판별" 자체가 운영 배포에서는 쟁점이 아님. 다만 야간 당번의 내부망 접속 경로는 별도 확인 (아래 1.5) |

- 실행기 성격 재정의로 **구매팀 질의서(10.4) 2번 "실행기 서버 권장 사양과 하드웨어·클라우드 비용"** 질문의 무게가 내려감. 다만 "0원"으로 보지는 않음 — 컴포넌트가 올라갈 호스트 자원과 다중화 구성 비용은 여전히 산정 대상

### 1.3 실행기 성격·가용성 재서술

- 실행기를 "무거운 운영 러너"가 아니라 **"검증·복호화·웹쉘 로컬 실행 컴포넌트"**로 비교표·품의서 용어를 통일함
- 비용표에서 "실행기 서버 대수·랙 공간" 항목을 삭제하지 않고 **"실행기 컴포넌트 호스팅 자원(기존 사내 호스트 활용 가능 여부 포함)"**으로 바꿔 적음
- 가용성은 유지. 표현만 "서버 증설"에서 **"컴포넌트 다중화 / 페일오버 시 승인·실행 연속성"**으로 변경
  - 확인 질문: 컴포넌트를 2개 이상 띄웠을 때 nonce 소진·서명 검증 상태가 공유되는가, 한쪽이 죽으면 진행 중 요청은 어떻게 되는가 (단일 nonce가 두 컴포넌트에서 이중 소진되지 않아야 함)

### 1.4 Tailscale 전제 변경

- 1차 공문·명세에서 전제했던 "Tailscale 접속 = 내부망 판별"은 **개발·테스트 단계 임시 구성**으로 정리
- 운영 배포 전제를 **웹 서비스↔실행기 mTLS, 내부망 대역은 당사 관리자가 설정**으로 변경
- 오세훈 대리의 "Tailscale 이미 쓰고 있어 붙이기 쉽다"는 1차 입장은 **시범·개발 단계에 한정**해 유지. 운영 배포 설치 절차서는 내부망 mTLS 기준으로 다시 받기로 함

### 1.5 보완 설명에도 여전히 남는 필수·확인 조건

| 번호 | 남는 조건 | 상태 | 사유 |
| --- | --- | --- | --- |
| 1 | 감사 로그 파일 내보내기 (CSV·엑셀) | **그대로 필수·미충족** | 실행기 성격·Tailscale과 무관. 5주차 화요일까지 실제 파일 확인 못 하면 후보 제외 원칙 유지 |
| 2 | AI 분석 데이터 흐름 | **그대로 필수·확인 불가** | 실행기가 검증·웹쉘 컴포넌트라는 설명은 "실행" 단계 이야기일 뿐, "AI가 Plan을 분석·생성하는 단계"에서 소스코드·프롬프트가 어디로 가는지는 별개. 오히려 더 명확히 받아야 함 |
| 3 | 승인 없는 실행 차단 | 그대로 필수·검증 전 | 시범 때 Plan 변조·서명 재사용 시험으로 직접 확인 |
| 4 | 실행기 컴포넌트 다중화·페일오버 | 재서술 후 확인 | 가용성 우려는 유지. 다중화 시 nonce·서명 상태 공유 방식 회신 요청 |
| 5 | 야간 당번 내부망 접속 경로 | 신규 확인 | 배포가 내부망 mTLS 전제라면, 새벽 외부에서 당번이 내부망에 어떻게 들어오는지(사내 VPN 등)와 그때 외부망 제한(4.4)이 어떻게 판별되는지 확인 |

### 1.6 1차 공문 대비 공문 재통보 범위

- 1차 공문(`letter-01-hansung-to-vendor.md`, 문서번호 한성소프트-구매-2026-1109-01)을 **철회하지 않고**, 보완 설명을 반영한 **재통보 공문**을 1건 더 발송
- 재통보 공문에 명시할 것:
  1. 실행기 성격 재정의 수용 → 우려 5번(이중화) 등급 하향·재서술, 질의서 2번(서버 사양·비용) 무게 하향
  2. Tailscale은 개발 test용, 배포는 내부망 mTLS → 우려 3번(Tailscale 판별) 대부분 해소
  3. 그럼에도 **빠지지 않는 필수 조건**(감사 로그 내보내기, AI 분석 데이터 흐름)과 신규 확인 항목(다중화 상태 공유, 야간 당번 내부망 경로)
- 기한·일정은 1차 공문 체계를 이어 감(2026. 11. 중순 이후). 필수 조건 미충족 시 도입 보류 원칙은 변동 없음

## 2. 논의 내용

### 2.1 실행기 성격 재정의

- 정우진: 업체 회신 요지는 "실행기는 무거운 러너가 아니라 서명 검증기 + E2EE 복호화 종단 + 웹쉘 로컬 실행 컴포넌트"라는 것. 1차 공문에서 우리가 쓴 "전산실 서버, 대수 산정" 전제가 과했다는 설명
- 김미경: 그럼 질의서 2번에서 물었던 "실행기 서버 권장 사양과 하드웨어·클라우드 비용"이 통째로 없어지는 거냐고 물음. 비용표에서 항목이 빠지면 나중에 숨은 비용으로 돌아올 수 있어 경계
- 결론: 항목을 삭제하지 않고 "실행기 컴포넌트 호스팅 자원"으로 바꿔 유지. 기존 사내 호스트로 올릴 수 있는지, 다중화하면 자원이 몇 배인지는 여전히 숫자로 받기로 함

### 2.2 가용성(이중화) 재서술

- 정우진: 컴포넌트가 가벼워졌다고 가용성 우려가 사라지는 건 아님. 이 한 컴포넌트가 죽으면 운영 작업 실행이 멈추는 건 똑같음. 다만 대응이 "서버 2대 증설"이 아니라 "컴포넌트를 여러 개 띄우고 페일오버"라는 쪽
- 김미경: 그럼 1차 공문 우려 5번을 지우는 게 아니라 문장을 바꾸는 거냐고 확인
- 정우진: 맞음. 지우면 안 됨. 단일 장애 지점이라는 사실은 그대로니까, 다중화했을 때 nonce가 두 컴포넌트에서 이중 소진되지 않는지, 한쪽이 죽으면 진행 중 요청이 어떻게 되는지를 물어야 함

### 2.3 Tailscale 전제

- 정우진: 업체 설명으로는 명세의 Tailscale은 개발·테스트용 임시 구성이고, 운영 배포는 웹 서비스↔실행기 mTLS에 내부망 대역은 우리 관리자가 설정하는 방식
- 김미경: 그럼 1차 공문 우려 3번 "Tailscale로 접속하면 내부망으로 판별되는지"는 어떻게 되냐고 물음
- 정우진: 운영 배포에서는 그 질문 자체가 거의 사라짐. Tailscale은 시범·개발 단계에만 쓰고, 배포는 내부망 mTLS니까. 오세훈 대리가 "Tailscale 이미 쓴다"고 한 건 시범 단계엔 유효하지만 운영 설치 절차서는 내부망 mTLS 기준으로 다시 받아야 함

### 2.4 그래도 남는 조건 — 감사 로그와 AI 분석 데이터 흐름

- 김미경: 숫자·근거를 다시 짚음. 실행기가 가벼워졌다는 설명은 "실행" 이야기지, 감사 로그를 파일로 내려받는 것과는 상관이 없음. 그건 1차 공문대로 5주차 화요일까지 실제 파일 확인 못 하면 제외 원칙 그대로라고 못 박음
- 정우진: 동의. 오히려 AI 분석 데이터 흐름은 더 또렷해져야 함. 실행기가 검증·웹쉘 컴포넌트라는 건 "실행" 단계이고, "AI가 Plan을 분석하고 만드는 단계"에서 소스코드·프롬프트가 사내인지 업체인지 제3자 AI인지는 별개 문제. 이게 필수 조건 2번(소스코드·고객 데이터 사내 보관)의 핵심
- 결론: 두 필수 조건은 보완 설명과 무관하게 그대로 유지. 재통보 공문에서 "빠지는 항목"과 "그대로 남는 항목"을 표로 분리

### 2.5 공문 재통보 방식

- 김미경: 1차 공문을 철회하고 새로 쓸지, 아니면 재통보로 보탤지 물음. 기록이 끊기면 안 된다는 입장
- 정우진: "한 문장으로 하면?" — 1차 공문은 살려 두고, 보완 설명으로 바뀐 부분만 재통보로 명확히 하자는 것
- 김미경: 그럼 문서번호와 시행일자는 1차 다음으로, 본문에 "어떤 우려가 내려갔고 어떤 조건이 그대로인지"를 표로 구분해 적겠다고 정리

### 2.6 야간 당번 내부망 경로 (신규)

- 정우진: Tailscale이 개발용으로 빠지면, 새벽 당번이 집에서 내부망으로 들어오는 경로를 다시 봐야 함. 배포가 내부망 mTLS 전제면 외부에서 당번이 어떻게 내부망에 붙는지(사내 VPN 등), 그때 외부망 제한(4.4)이 어떻게 판별되는지가 비어 있음
- 김미경: "그거 되돌릴 수 있어요?"가 아니라 "그거 새벽에 되긴 해요?"가 궁금하다고 함. 신규 확인 항목으로 추가
