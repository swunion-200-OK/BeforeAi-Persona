## 2. MBTI와 성향

### 2.1 ENTJ 특징이 드러나는 모습

- **외향(E)**: 회의를 먼저 열고 먼저 말함. 화이트보드 앞에 서는 걸 좋아함
- **직관(N)**: "이게 1년 뒤 어떻게 될지"를 먼저 그림. 당장의 불편보다 구조를 봄
- **사고(T)**: 코드 리뷰에서 감정이 섞인 말을 쓰지 않으려 하지만, 결과적으로 팀원들은 "차갑다"고 느끼기도 함
- **판단(J)**: 분기 목표를 OKR로 쪼개고, 매주 월요일 진척률을 숫자로 공유함

### 2.2 MBTI를 대하는 태도

- 슬랙 프로필에 "ENTJ"를 적어 둠. 팀원들이 대화 방식을 맞춰 주길 바라는 의도
- 김미경 차장이 ISTJ라는 걸 듣고 "그래서 숫자 들고 가면 통하는구나" 하고 납득함
- 팀 빌딩 때 MBTI 놀이를 하긴 하지만 채용·배치에 쓰는 건 반대

### 2.3 성격 요약

| 강점 | 약점 |
| --- | --- |
| 결정이 빠름. 회의 끝에 반드시 "누가, 언제까지"를 정함 | 기다리는 걸 못 참음. 구매·법무 일정에 자주 답답해함 |
| 구조를 잘 봄. 장애가 나면 원인보다 재발 방지 구조를 먼저 그림 | 팀원의 작은 실수에도 구조 문제로 키워 말해서 부담을 줌 |
| 책임을 피하지 않음. 팀 사고는 본인 이름으로 보고 | 일을 너무 많이 떠안아 번아웃 직전까지 간 적이 있음 |
| 기술 트렌드에 밝음. AI 도구를 팀에 가장 먼저 들임 | 새로운 것에 대한 기대가 커서 위험을 과소평가한 적이 있음 |
| 설득력이 있음. 본부장 보고를 잘함 | 상대가 이해하지 못하면 설명을 줄이고 결론만 반복하는 버릇 |

### 2.4 스트레스 반응

- 일이 막히면 오히려 더 많은 일을 벌임. 사이드 프로젝트를 새로 시작하는 식
- 장애 대응 중에는 말이 짧아지고 명령조가 됨. 끝나면 팀 채널에 "아까 말 세게 해서 미안" 하고 사과함
- 스트레스가 쌓이면 새벽에 탄천을 10km 뜀

### 2.5 의사결정 스타일

1. 문제를 한 문장으로 정의한다 ("운영에 닿는 AI 작업은 사람이 서명한 것만 실행된다")
2. 선택지를 셋으로 줄인다 (사기 / 만들기 / 안 하기)
3. 각 선택지의 1년 비용을 사람 시간으로 환산한다
4. 결정하고, 틀리면 빨리 되돌릴 방법을 같이 정한다
5. 팀원 반대가 있으면 2주 시범 후 다시 보자고 제안한다

- 집에서 일하는 시간이 길어 아이들 하교와 학원 일정을 주로 챙김. 우진은 이 점에 늘 미안해함

- 우진이 주말에도 노트북을 열면 "오늘은 두부한테 키보드 양보해"라고 말함

## 4. 성장 배경과 경력

### 4.1 어린 시절과 학창 시절

- 해운대에서 1남 1녀 중 막내로 자람. 아버지 교대 근무 때문에 어머니 가게에서 숙제를 하며 컸음
- 중학교 때 아버지가 사 준 중고 PC로 게임을 하다가 프로그래밍을 시작함
- 고등학교 때 정보올림피아드 지역 예선 통과. 본선에서는 탈락
- 대학에서 학회 회장을 맡으며 처음으로 "사람을 움직이는 일"이 재미있다는 걸 알게 됨

### 4.2 경력

| 기간 | 회사 | 직무 | 배운 것 |
| --- | --- | --- | --- |
| 2007~2011 | 중견 SI 기업 | 금융권 차세대 프로젝트 개발자 | 금융권 보안 요구, 변경 관리 절차, 야근 문화 |
| 2011~2016 | 국내 대형 포털 | 결제 플랫폼 백엔드 개발 → 파트 리드 | 대규모 트래픽, 장애 회고 문화, 코드 리뷰 |
| 2016~2018 | 핀테크 스타트업 (공동 창업) | CTO | 빨리 만드는 법, 그리고 빨리 만들다 생긴 사고의 대가 |
| 2018~2019 | 휴식·프리랜서 | 기술 자문 | 번아웃 회복, 가족과의 시간 |
| 2019~현재 | ㈜한성소프트 | 시니어 개발자 → 플랫폼개발팀장 (2022) | 금융 고객사 요구와 개발 속도의 균형 |

### 4.3 기억에 남는 성공과 실패

**실패: 2017년 스타트업 운영 DB 사고**
- 배포 스크립트의 환경 변수가 잘못 잡혀 스테이징 대신 운영 DB 마이그레이션이 실행됨
- 고객 데이터 일부가 6시간 동안 조회되지 않았고, 투자사 신뢰를 잃는 계기가 됨
- 회사는 1년 뒤 정리됨. 우진은 지금도 "운영에 닿는 명령은 사람이 내용을 보고 승인해야 한다"는 원칙을 이 사고에서 배웠다고 말함

**성공: 2023년 배포 파이프라인 개편**
- 수동 배포(월 2회, 야간 작업)를 자동 배포(주 5회 이상)로 바꿈
- 배포마다 변경 내역과 승인자를 남기도록 해서, 그해 금융 고객사 수탁사 점검에서 "변경 관리" 항목 지적이 0건이 됨
- 이 일로 본부장 신뢰를 얻었고, AI 도구 공식 도입도 우진이 주도함

**위기: 지난달 AI 스크립트 사고 위기**
- 팀 신입 개발자가 AI 에이전트에게 "테스트 데이터 정리"를 맡겼는데, 에이전트가 만든 스크립트의 접속 정보가 운영 DB였음
- 인프라팀 오세훈 대리가 비정상 접속을 보고 막음. 실행됐다면 금융 고객사 데이터 일부가 삭제될 수 있었음
- 우진은 본부장에게 "팀장 관리 책임"으로 직접 보고하고, 일주일 안에 통제 도구 도입 계획을 냄
- 2017년 사고가 떠올라 그 주에 잠을 거의 못 잠

## 9. 가치관

- **"AI가 한 건 사람이 설명할 수 있어야 그 사람 거다."** 아들에게 한 말이 그대로 팀 원칙이 됨

- **"되돌릴 수 있으면 빨리, 못 되돌리면 천천히."** 위험도 분류에 대한 본인의 기준

## 10. 본 서비스 도입 검토

### 10.1 우진이 정의한 문제

- 운영 환경(DB, 배포, 고객 데이터)에 닿는 AI 작업은 사람이 내용을 보고 서명한 것만 실행되어야 한다
- 그 외 작업(문서, 경미한 코드 수정)은 지금 속도를 유지해야 한다
- 누가 무엇을 승인했는지 금융 고객사 점검에서 증명할 수 있어야 한다

### 10.2 선택지 비교 (우진이 본부에 보고한 표)

| 선택지 | 1년 비용 추정 | 장점 | 단점 |
| --- | --- | --- | --- |
| 본 서비스 도입 | 라이선스 + 실행기 서버 + 설치 지원 (구매팀 견적 대기) | 승인·서명·감사·킬 스위치가 이미 있음. 실행기가 웹 서비스를 믿지 않는 구조 | 업체 업력. 승인 정책이 우리 방식과 맞는지 시범 필요 |
| 자체 구축 | 개발 3명 × 6개월 + 유지 1명 상시 (약 4억 원 상당) | 우리 방식대로 만들 수 있음 | 플랫폼팀 로드맵 6개월 지연. 보안 설계 검증을 우리가 책임짐 |
| AI 도구 기업 요금제 + 기존 결재·CI 승인 | 추가 비용 적음 | 익숙함 | AI가 실제로 실행한 내용과 결재한 내용이 같은지 보장할 수 없음 |

### 10.3 우진이 명세를 읽고 좋게 본 점

- **Plan 해시를 실행기가 직접 만든다**: 웹 서비스가 털려도 승인받지 않은 Plan은 실행되지 않음
- **서명을 실행기 공개키로 암호화한다**: 중간에서 서명을 바꿔치기할 수 없음
- **nonce 1회 소진**: 같은 승인으로 두 번 실행하는 일이 없음
- **킬 스위치는 서명 없이 즉시**: 장애 대응 때 가장 필요한 기능
- **외부망에서는 CODE_MINOR·CODE_FEATURE만 승인 가능**: 재택 중 운영 DB를 건드릴 수 없음
- **웹 코드 에디터도 승인 절차를 거친다**: "에디터로 몰래 고치기" 우회로가 없음
- **규모 프리셋**: 200명 회사에 맞는 기본값으로 시작할 수 있음

### 10.4 우진이 걱정하는 점

| 걱정 | 명세 기준 상황 | 우진의 질문 |
| --- | --- | --- |
| 승인 대기 시간 | 필요한 승인이 모이면 자동 실행 | "승인 대기 평균 시간을 대시보드에서 볼 수 있나요?" |
| Plan 수정 시 재승인 | `PENDING_APPROVAL`에서 Plan을 고치면 기존 서명 모두 무효 | "오타 하나 고쳐도 처음부터 다시 받나요?" |
| 야간 당번의 외부망 제한 | 외부망에서는 코드 수정만 승인 가능, 배포·DB는 막힘 | "새벽 장애 때 집에서 핫픽스 배포 승인은 어떻게 하죠? Tailscale 접속이면 내부망으로 보나요?" |
| 본인 승인 범위 | 요청자 본인 승인이 허용된 작업은 제출과 동시에 승인 | "LOW 작업은 본인 승인으로 끝나게 설정할 수 있나요?" |
| 담당자 2명 이상 | 2명 미만으로 줄이면 `409 OWNER_MINIMUM` | "휴가철에 담당자 둘 다 없으면요?" |
| 분석 재시도 3회 제한 | 넘으면 `409 RETRY_LIMIT` | "3회 넘으면 그 요청은 버리고 새로 만들어야 하나요?" |
| 기존 도구 연동 | 명세에 Slack 알림은 있고 깃허브·CI 연동은 없음 | "PR 리뷰와 승인을 중복으로 하게 되지 않나요?" |
| 실행기 장애 | 연결 실패 시 `502 EXECUTOR_UNAVAILABLE` | "실행기가 죽으면 모든 운영 작업이 멈추는데, 이중화는요?" |
| 금지 규칙 해제 | 실행기 로컬 콘솔에서 관리자가 다시 확인해야 해제 | "좋은 설계지만, 로컬 콘솔 접근 절차를 우리 인프라팀이 운영할 수 있을지" |

### 10.5 시범 사용 계획 (우진이 작성)

| 주차 | 내용 | 측정 지표 |
| --- | --- | --- |
| 1주 | 저장소 3개 연결, 팀원 6명만 사용, 규모 프리셋 `MEDIUM` | 설치 소요 시간, 키 등록 완료율 |
| 2주 | 일상 작업 전부를 본 서비스로 요청 | 작업 유형 분포, 승인 대기 평균·최대 시간 |
| 3주 | 야간 당번 1명 포함, 외부망 승인 시나리오 테스트 | 외부망에서 막힌 작업 수, 우회 시도 수 |
| 4주 | 일부러 잘못된 Plan 제출, 킬 스위치, 검증 실패 시나리오 테스트 | `VERIFICATION_FAILED` 감지율, 킬 스위치 반응 시간 |
| 종료 | 팀원 설문 (김미경 차장 비교표의 "현업 만족도" 항목에 반영) | 만족도, "계속 쓰고 싶다" 비율 |

### 10.6 성공 기준

- 운영 DB·배포 작업 100%가 승인 서명 후 실행됨
- LOW 작업의 요청부터 실행까지 중앙값 5분 이내
- 시범 기간 팀원의 우회 시도 0건 (AI 도구로 직접 운영 접속)
- 팀원 설문 "계속 쓰고 싶다" 70% 이상

## 11. 고민과 불안

- **팀원 이탈**: 생산성 높은 김태현 책임 같은 사람들이 "절차 때문에 일 못 하겠다"며 불만을 가지면 이직으로 이어질 수 있음
- **CTO 설득**: 자체 구축을 원하는 CTO에게 "사는 게 맞다"는 근거를 내야 함
- **책임 이중 부담**: 도입을 주도했으니 도입 후 사고가 나도 본인 책임, 생산성이 떨어져도 본인 책임
- **사고 재발 공포**: 2017년과 지난달 일이 겹쳐, 운영 DB 관련 알림이 오면 심장이 먼저 뜀
- **구매 일정**: 6주가 길게 느껴짐. 그동안 다른 팀원이 비슷한 실수를 할까 봐 임시로 운영 DB 접근 권한을 회수함 (팀원 불만 발생)

- "AI를 안전하게 쓰는 팀"이라는 사례를 만들어 다른 팀과 고객사에 보여 주는 것
- 금융 고객사 점검에서 "AI 변경 관리" 항목을 선제적으로 설명하는 것
- 최민준 사원 같은 신입이 겁먹지 않고 AI 도구를 쓸 수 있는 환경
- 차기 본부장 평가에서 "구조를 만드는 리더"로 인정받는 것

## 13. 커뮤니케이션 방식

### 13.1 업체를 대할 때

- 데모 첫 10분 안에 API 명세와 아키텍처 문서를 요청함
- 영업 담당보다 엔지니어와 직접 이야기하길 원함. "기술 담당자 슬랙 채널 열어 주실 수 있나요?"
- "로드맵에 있습니다"라는 답에는 "분기와 이슈 번호를 알려 주세요"라고 되물음
- 보안 구조 설명에서 한 번이라도 틀린 말이 나오면 신뢰를 크게 깎음

### 13.2 팀원과

- 결정은 빠르게 하되 이유를 슬랙 스레드에 남김
- 반대 의견은 공개 채널에서 받고, 개인 피드백은 1:1에서
- 도입 반대 의견을 가진 김태현 책임을 시범 사용 6명에 일부러 넣음. "제일 불만 많은 사람이 써 봐야 진짜 문제가 나온다"

### 13.3 김미경 차장과의 관계

- 처음 도입 요청을 슬랙 세 줄로 보냈다가 "요건서로 다시 주세요"라는 답을 받고 당황함
- 이후 미경에게 갈 때는 비용 추정표와 시범 계획을 문서로 들고 감
- 지금은 "김 차장님이 통과시킨 계약은 나중에 문제가 없다"고 팀원들에게 말함
- 미경의 딸이 판교 개발자라는 걸 알고, 미경이 용어를 물어볼 때 "따님한테 이렇게 설명해 보세요"라고 비유를 같이 줌

### 13.4 자주 하는 말

- "한 문장으로 하면 뭐예요?"
- "그거 되돌릴 수 있어요?"
- "누가, 언제까지?"
- "2주만 써 보고 다시 얘기하죠."
- "구조 문제지 사람 문제 아닙니다."

## 14. 반대로 돌아설 수 있는 사유

- 시범 기간 LOW 작업 승인 대기가 5분을 자주 넘는 경우
- 보안 구조 설명과 실제 동작이 다른 경우 (예: 웹 서비스가 envelope을 열 수 있다는 사실이 드러남)
- API 명세가 실제 응답과 다르거나 오류 코드가 부정확한 경우
- 실행기 설치에 인프라팀 인력이 2주 넘게 묶이는 경우
- 업체 엔지니어와 직접 소통할 창구가 없는 경우
- 야간 장애 대응 시나리오에 답이 없는 경우

## 15. 사용 시나리오

### 시나리오 1: 명세 검토

1. 업체에서 받은 API 명세를 퇴근 후 집에서 끝까지 읽음
2. 2.3 해시 대상에 `title`이 빠진 것을 보고 "제목은 바꿔도 재승인이 안 되겠네, 의도한 거겠지"라고 메모함
3. 5장 실행기 검증 순서를 보고 처남에게 캡처를 보내 의견을 물음
4. 다음 날 아침 질문 12개를 정리해 업체 기술 담당자에게 보냄

### 시나리오 2: 시범 2주차, 일상 작업

1. 김태현 책임이 로그 메시지 수정을 요청함. CODE_MINOR, LOW
2. 본인 승인 설정 덕분에 제출과 동시에 승인되고 2분 만에 실행 완료
3. 같은 날 박나래 선임의 DATA_READ 요청은 같은 부서 다른 사람 승인이 필요해 40분 대기
4. 우진은 DATA_READ 승인 기준을 조정할 수 있는지 승인 기준표 화면을 확인함

### 시나리오 3: 새벽 장애 대응

1. 새벽 3시, 당번 윤소희 책임이 집에서 장애 알림을 받음
2. AI로 핫픽스 Plan을 만들었지만 DEPLOY 작업이라 외부망에서 승인이 막힘 (`blockedReason: INTERNAL_NETWORK_ONLY`)
3. 윤소희 책임이 Tailscale로 접속해 내부망으로 판별되는지 확인함. 내부망으로 인정되어 담당자인 우진에게 Slack 알림이 감
4. 우진이 깨어나 노트북을 열고 Plan을 확인한 뒤 서명함. 알림부터 실행까지 12분
5. 아침 회고에서 "새벽 승인권자 당번"을 따로 둘지 논의함

### 시나리오 4: 일부러 깨 보기

1. 시범 4주차, 이수빈 수석과 함께 웹 서비스 DB에서 Plan 내용을 직접 바꿔 실행 요청을 보냄
2. 실행기가 `PLAN_HASH_MISMATCH`로 거부하고, Slack 경보가 관리자와 우진에게 감
3. 같은 승인 envelope을 다시 보내자 `NONCE_ALREADY_USED`로 거부됨
4. 우진은 이 결과를 캡처해 CTO 보고 자료 첫 장에 넣음. "웹 서비스가 털려도 실행은 안 됩니다"

### 시나리오 5: CTO 보고

1. 자체 구축 추정치(3명 × 6개월 + 유지 1명)와 본 서비스 견적을 나란히 놓음
2. 시나리오 4의 검증 결과로 "보안 설계를 우리가 처음부터 검증하지 않아도 된다"고 설명함
3. CTO가 "그럼 우리 팀이 실행기 코드를 볼 수는 있어?"라고 물음. 우진은 업체에 소스코드 기탁 여부를 질의서에 추가함
