## 2. MBTI와 성향

### 2.1 ISTP 특징이 드러나는 모습

- **내향(I)**: 회의에서 말이 짧음. 할 말을 미리 정해 두고 그것만 말함
- **감각(S)**: 장애 보고서는 "몇 시 몇 분에 무엇이 일어났다"로만 씀. 추측은 따로 표시함
- **사고(T)**: 협력사 개발자가 사과하면 "사과는 됐고 로그 주세요"라고 말함. 본인은 차갑다는 평을 알고 있음
- **인식(P)**: 계획보다 현장 대응에 강함. 문서화는 미루다가 장애가 난 뒤 몰아서 함. 이번 건으로 이 습관을 고치려 함

### 2.2 MBTI를 대하는 태도

- 팀원들이 회식 자리에서 시켜서 해 봄. "그냥 그런가 보다" 정도로 받아들임
- 노경태 부장이 ESTJ라는 말을 듣고 "그래서 회의를 본인이 다 정리하려고 하는구나"라고 생각함
- 협력사 PM이 "팀장님 ISTP시죠? 그래서 말씀이 짧으신 거죠"라고 했을 때 대답하지 않음

### 2.3 성격 요약

| --- | --- |
| 장애 원인을 빨리 찾음. 9월 사고 때 원인 특정까지 2시간 10분 | 문서화를 미룸. 배치 스크립트 1,300개 중 설명서가 있는 건 200개 남짓 |
| 명세와 로그를 끝까지 읽음. 업체 문서의 절 번호를 외워서 말함 | 남에게 일을 맡기지 못하고 새벽 호출을 본인이 받음 |

### 2.4 스트레스 반응

- 야간 호출이 주 3회를 넘으면 잠을 못 자고 출근길에 커피를 두 잔 마심
- 말이 더 짧아지고 메신저 답을 "확인", "보류", "반려" 한 단어로 함
- 쌓이면 일요일에 혼자 청라 호수공원을 두 바퀴(약 12km) 걷거나, 베란다에서 고장 난 가전을 분해함
- 2025년 여름 야간 호출이 몰렸을 때 회사 상담 프로그램(EAP)을 6회 이용함. 팀원에게는 말하지 않음

### 2.5 의사결정 스타일

1. 사고가 다시 나는 경로를 먼저 그린다 ("어디로 들어와서 어디를 건드리고 누가 모르는가")
2. 사람이 아니라 계정, 키, 로그 단위로 통제 지점을 찾는다
3. 명세나 매뉴얼에 적힌 것만 "된다"고 본다. 영업 자료는 참고만 함
4. 새벽 세 시 상황에서 돌려 본다. 그 시간에 안 되는 통제는 통제가 아니라고 봄
5. 결정은 늦은 편이지만, 정하고 나면 운영 절차서까지 직접 씀

## 10. 본 서비스 도입 검토

### 10.1 선영이 정의한 문제

- WMS·ERP 운영 환경(배치 스크립트, 운영 DB, 배포)에 닿는 변경은 사람이 내용을 보고 서명한 것만 실행되어야 한다
- 그 서명은 협력사 개발자가 철수하는 날 바로 무효가 되어야 한다
- 새벽에도 같은 절차가 돌아가야 하고, 화주사 감사관에게 기록을 파일로 낼 수 있어야 한다

### 10.2 선택지 비교 (선영이 탁명진 본부장에게 보고한 표)

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 본 서비스 | 실행기가 Plan 해시를 직접 만들고 승인 서명을 검증. 킬 스위치, 금지 작업, 감사 로그가 이미 있음 | 업력. 레거시 저장소와 저장소 밖 스크립트 정리 필요. Slack만 지원 |
| PAM 확장 + 변경관리 결재 연동 | 이미 쓰는 업체, 운영자 익숙함 | 결재 문서와 실제 실행 명령이 연결되지 않음. "결재받은 것과 다른 걸 실행"을 막을 수 없음 |
| AI 도구 금지 + 계약 조항 강화 | 비용 적음 | 2026년 3월 금지 통보 후에도 9월 사고. 지키는지 볼 수단이 없음 |

### 10.3 선영이 명세를 읽고 좋게 본 점

| 기능 | 명세 근거 | 선영의 평가 |
| --- | --- | --- |
| 실행기가 Plan 해시를 JCS 정규화 + SHA-256으로 직접 만들고 웹 서비스 해시를 쓰지 않음 | 2.3, 5장 | 웹 서비스나 중간 경로가 바뀌어도 승인받지 않은 내용은 실행 안 됨. 9월처럼 "승인 후 몰래 바꾸기"를 막음 |
| 실행기 검증 6단계 (복호화, 해시, 서명, nonce, 필요 승인권자, 금지 작업) | 5.1 | 하나라도 실패하면 웹쉘을 열지 않음. 실패 사유가 `failedChecks`로 남음 |
| 폐기된 키는 `KEY_NOT_REGISTERED`로 거부 | 5.1, 1.2 | 철수한 협력사 개발자 키로 만든 승인은 실행기에서 막힘 |
| 공개키 폐기가 실행기에 바로 반영 | 3.2 `DELETE /admin/signing-keys/{keyId}` | 철수일 당일 처리 가능. 다만 계정 비활성화와 따로임 |
| 키 등록에 관리자 서명 필요 | 3.2 `POST /admin/signing-keys/{keyId}/register` | 협력사 PM이 마음대로 키를 등록할 수 없음 |
| 외부망에서는 `CODE_MINOR`·`CODE_FEATURE`만 승인, 나머지는 `blockedTaskIds` | 4.4, 3.6 | 집이나 외부에서 운영 DB·배포 승인 불가 |
| 외부망 로그인은 OTP, 30분 비활동 만료 | 1.1 | 협력사 개발자 노트북 분실 시 피해 범위가 줄어듦 |
| 킬 스위치는 서명 없이, 외부망에서도 동작 | 4.6 | 새벽에 집에서도 잘못된 실행을 멈출 수 있음 |
| 전사 일괄 중단 | 3.2 `POST /admin/kill-all` | 9월 같은 상황에서 센터 전체 AI 작업을 한 번에 멈춤 |
| 금지 규칙 해제는 실행기 로컬 콘솔에서 관리자가 다시 확인 | 3.4 `RELEASE_PENDING`, 5장 `RELEASE_PENDING_LOCAL` | 원격에서 통제를 풀 수 없음 |
| 한 작업에 여러 부서와 여러 승인 규칙 | 2.2 `relatedDepartments`, `requiredApprovers.rule` | 출고 배치 변경에 WMS개발팀과 센터를 같이 걸 수 있음 |
| 웹 코드 에디터도 승인·서명을 거침, 저장소에 직접 쓰지 않음 | 3.8, 4.7 | "급해서 서버에서 바로 고치기"를 대신할 통로가 생김 |
| 상태를 바꾸는 모든 API의 감사 로그에 접속 환경·IP | 1.1, 4.8 | 9월처럼 "누가 했는지 모름"이 없어짐 |
| 실행기 연결 실패 시 상태 유지 | 4.3 `502 EXECUTOR_UNAVAILABLE` | 장애 때 승인 절차가 저절로 풀리지 않음 |

## 13. 커뮤니케이션 방식

### 13.1 업체를 대할 때

- 데모에서 영업 담당 말이 길어지면 "명세 몇 절이에요?"라고 끊음
- 기술 담당에게 새벽 장애 시나리오를 하나 주고 그 자리에서 답을 들음
- "다음 버전에 됩니다"는 "지금은 안 된다"로 기록함
- 오류 코드 하나라도 명세와 실제가 다르면 그 업체의 다른 말도 다시 확인함

### 13.2 팀원·협력사와

- 팀원에게는 결론과 이유를 한 줄씩. 칭찬은 서툴러서 커피로 대신함
- 협력사 개발자에게 직접 지시하지 않고 함지훈 PM을 통해 요청함 (법무 권고)
- 장애 회고에서는 이름을 쓰지 않고 "계정 A", "스크립트 B"로 씀

### 13.3 노경태 부장과의 관계

- 2023년 협력사 재편 때 선영은 "인원 단가만 보고 바꾸면 교육 부담이 운영팀으로 온다"고 반대했음. 노 부장은 숫자로 밀어붙였고 선영은 한동안 노 부장과 말을 섞지 않음
- 그런데 2024년 감사 지적 0건의 근거가 노 부장이 2016년 이후 넣은 계정 반납 조항이었다는 걸 알고 생각이 조금 바뀜
- 선영은 노 부장의 "그래서 3년이면 얼마예요?"가 피곤하지만, 그 질문에 답을 들고 가면 결정이 빠르다는 걸 앎
- 노 부장이 협력사 비용 분담을 꺼내면 선영은 "사고 비용 4,900만 원 얘기는 하시면서 통제 비용은 아끼자는 거냐"고 받아침
- 둘 다 9월 16일을 다시 겪고 싶지 않다는 점에서는 같음

## 14. 반대로 돌아설 수 있는 사유

- 철수자 키 폐기가 실행기에 바로 반영되지 않거나, 폐기된 키의 기존 승인으로 실행이 되는 경우
- 웹 서비스가 승인 envelope을 열어 볼 수 있다는 사실이 드러나는 경우 (명세 4.5와 다름)
- 실행기 설치에 Tailscale 외 다른 외부 연결이 숨어 있는 경우
- AI 분석 과정에서 소스코드나 화주사 주문 데이터가 회사 밖으로 나가는데 설명하지 않는 경우
- 야간 긴급 변경 시나리오에 답이 없는 경우
- 비용을 맞추려고 협력사 계정을 빼자는 결론이 나는 경우

## 15. 사용 시나리오

### 시나리오 1: 새벽 웨이브 배치 긴급 수정

1. 새벽 02:20, 화주사가 마감 시각 변경을 긴급 요청함. 새온정보기술 야간 대기 개발자가 AI로 `wave_alloc.sh` 수정 Plan을 만듦
2. 작업은 `CODE_FEATURE`(스크립트 수정)와 `DEPLOY`(배치 서버 반영) 두 개. `DEPLOY`는 `HIGH`
3. 당번 하승우 대리가 집에서 승인 화면을 열자 `DEPLOY`가 `blockedTaskIds`에 들어가 있고 `blockedReason: "INTERNAL_NETWORK_ONLY"`
4. 하 대리는 SSL VPN으로 다시 접속해 내부망으로 판별되는지 확인함. 회사 대역으로 인정되면 승인 가능
5. 출고 배치라 이천센터 야간 운영책임자(센터 `DEPT_MANAGER`)의 승인도 필요함. 센터 사무실에서 서명
6. 02:58 실행 완료. 선영은 아침에 감사 로그로 경위를 확인함

### 시나리오 2: 협력사 개발자 철수

1. 금요일 17:00, 새온정보기술 개발자 1명 철수. 구매팀 엄태준 대리의 통보 메일 도착
2. 변재민 파트장이 `PATCH /admin/users/{userId}`로 계정을 비활성화하고 `DELETE /admin/signing-keys/{keyId}`로 키를 폐기함
3. 그 사람이 오후에 서명해 둔 승인이 `PENDING_APPROVAL` 요청에 남아 있음. 다른 승인이 모여 실행 요청이 가자 실행기가 `KEY_NOT_REGISTERED`로 거부하고 요청은 `VERIFICATION_FAILED`
4. 선영은 이 결과가 맞다고 보지만, 다른 정상 작업까지 같이 멈춘 점을 함지훈 PM에게 설명해야 함

### 시나리오 3: 화주사 감사 증적

1. 2027년 1월 감사 전, 길예진 주임이 파일럿 기간 승인 기록을 정리함
2. `GET /audit-logs?projectId=&from=&to=`로 검색은 되지만 파일로 받을 수 없어 100건씩 화면을 넘기며 엑셀에 옮김
3. 승인자, 접속 환경, IP, 검증 실패 항목을 직접 붙여 넣는 데 이틀이 걸림
4. 선영은 이 작업 시간을 노경태 부장에게 숫자로 줌. 노 부장은 이를 협상 자료로 씀

### 시나리오 4: 실행기 장애

1. 본사 전산실 UPS 점검 중 실행기 서버가 내려감
2. 웹 서비스에서 제출하면 `502 EXECUTOR_UNAVAILABLE`, 요청 상태는 그대로
3. 그사이 평택센터에서 긴급 변경이 필요해짐. 선영은 "실행기를 우회해 서버에서 직접 고치기"를 허용할지 판단해야 함
4. 이 시나리오에 업체 답이 없으면 비상 절차(수동 변경 + 사후 기록)를 따로 만들어야 함

### 시나리오 5: 노사협의회 사전 설명

1. 육정란 근로자위원 대표가 "감사 로그에 사람 이름과 IP가 남는다"는 설명을 듣고 현장 PDA 위치 기록 건을 꺼냄
2. 선영은 이용 대상이 IT본부와 협력사 개발자, 현업 승인자뿐이고 현장 PDA와 연결되지 않는다고 설명함
3. 대시보드 `scope=ME`, 감사 로그 역할별 범위(3.9)를 보여 주며 "부서 관리자도 자기 부서 것만 본다"고 말함
4. 육 위원이 "그럼 그 기록을 인사 평가에 안 쓴다는 걸 문서로 주세요"라고 요구함
