## 1. 결정 사항

### 1.1 결론

- 업체 보완 설명 2건을 **검토 접수**하되, 1차 공문(제2026-0412호)의 **필수 조건 5개와 검수 시험표(붙임 2)는 그대로 유지**함. 설명으로 우려의 "성격"이 바뀐 것이지 검수 면제는 아님
- 실행기 우려는 **"서버 2대 산정"에서 "컴포넌트 다중화/페일오버 설계 확인"으로 재서술**함. 24시간 물류센터 특성상 가용성 요구 수준은 낮추지 않음
- Tailscale 우려는 **개발 test 단계 임시 구성, 배포 운영은 사내 내부망 mTLS**라는 설명으로 보안 심의 쟁점의 범위가 줄어든 것으로 봄. 다만 보안 심의 대상 자체가 사라진 것은 아니며, SSL VPN 내부망 판별(필수 조건 4번)은 여전히 파일럿 시험 대상임
- 2차 공문(제2026-0415호)을 11월 13일(금) 업체 1차 회신과 함께 정리할 수 있도록, 반영 문구를 오늘 확정함

### 1.2 보완 설명 1 — 실행기 성격 재정의 수용 결과

업체가 전달한 설명: 실행기는 무거운 별도 인프라 러너가 아니라 아래 세 가지 역할의 경량 컴포넌트.

| 역할 | 업체 설명 | 당사 재평가 |
| --- | --- | --- |
| (a) 서명 검증기 | 실행기가 Plan 해시를 **자체 생성**(JCS 정규화 + SHA-256)하고 Ed25519 서명과 nonce를 검증 | 명세 2.3·5.1과 일치. 1차 공문 도입 사유 1·2번의 근거가 더 분명해짐. 웹 서비스 해시를 쓰지 않는다는 점 재확인 |
| (b) E2EE 복호화 | 승인 envelope을 비대칭키 종단간 암호화로 받아 **실행기 공개키로만 복호화**, 웹 서비스는 열지 못함 | 명세 2.4·4.5와 일치. 차선영의 "반대 사유"(웹 서비스가 envelope을 연다) 중 하나가 설명으로 해소되는 방향. 단, 파일럿 변조·재사용 시험(붙임 2의 5·6번)으로 실제 확인 |
| (c) 웹쉘 세션 | 검증 6단계 통과 시 웹쉘 세션으로 로컬 작업 수행 | 명세 5장과 일치. "경량"이라는 표현은 서버 비용 산정에만 쓰고, 가용성 요구를 낮추는 근거로는 쓰지 않음 |

- 성격이 "별도 인프라 러너"가 아니라 "검증기 + 복호화 + 웹쉘 세션 경량 컴포넌트"로 정리되면서, 1차 공문 우려 4번("실행기 단일 구성")의 **표현을 "서버 몇 대"에서 "컴포넌트 다중화와 페일오버"로 바꿈**
- 다만 경량이라도 **그 컴포넌트가 죽으면 6개 센터 긴급 변경이 멈춘다는 사실은 그대로**임. 경량 여부와 가용성은 다른 문제로 분리해 다룸

### 1.3 실행기 다중화/페일오버 재서술 (1차 공문 희망 요청 3번 갱신)

- 1차 공문 "실행기 2대 구성(본사 전산실 + 이천센터)" 요구를 **"실행기 컴포넌트의 다중화(active-standby 또는 active-active)와 페일오버"** 요구로 바꿈. 물리 서버 대수는 업체 설계에 맡기고, 당사는 **가용성 결과**를 요구함
- 경량 컴포넌트라면 본사 전산실 1대 + 이천센터 1대처럼 물리 분리든, 한 거점에 이중 인스턴스든 업체가 제안하되, 아래를 서면으로 받음

| 확인 항목 | 요구 내용 |
| --- | --- |
| 전환 방식 | 주 컴포넌트 장애 시 예비 컴포넌트로 전환하는 방식(수동/자동), 전환 소요 시간 |
| 상태 이전 | 실행기 공개키·개인키, 보관 Plan 해시, 사용한 nonce 소진 상태, 금지 규칙·정책 버전이 예비 컴포넌트에도 이어지는지 |
| 중복 실행 방지 | 전환 중 같은 승인 envelope이 양쪽에서 실행되지 않는지 (nonce 일원화 또는 잠금) |
| 복호화 키 | E2EE가 실행기 공개키로만 열린다면, 예비 컴포넌트의 공개키를 승인 envelope 암호화 대상에 어떻게 포함하는지(키 공유인지, 다중 수신자 암호화인지) |
| 장애 중 처리 | 전환 중 제출·승인 요청이 `502 EXECUTOR_UNAVAILABLE`로 상태 유지되는지(4.3), 전환 후 재처리 경로 |
| 비용 | 다중화 구성 시 구축비 1,500만 원 포함 여부, 거점 추가 시 증분 비용 |

- 24시간 운영 가용성 요구는 **붙임 3(야간 장애 지원)과 묶어** 유지. 단일 구성으로 시작하더라도 파일럿에서 주 컴포넌트를 실제로 내려 `502 EXECUTOR_UNAVAILABLE` 상태 유지와 비상 변경 절차를 시험함(붙임 2의 8번). `EXECUTOR_UNAVAILABLE`에서 승인 통제를 풀고 작업하는 것은 복구로 인정하지 않음(1차 공문 유지)

### 1.4 보완 설명 2 — Tailscale 재평가 결과

업체가 전달한 설명: Tailscale은 **개발/테스트 단계 임시 구성**이고, 운영 **배포는 고객사(대진로지스) 내부망 연결**(웹 서비스↔실행기 mTLS, 내부망 대역은 관리자 설정).

| 1차 공문 우려(제2026-0412호 4-다-5번) | 업체 설명 | 재평가 |
| --- | --- | --- |
| "Tailscale을 안 쓰는데 보안 심의를 새로 받아야 함" | 배포는 사내 내부망 mTLS이므로 Tailscale 조정 서버가 운영 경로에 없음 | **완화.** 외부 조정 서버 상시 통신이라는 심의 쟁점이 줄어듦. 다만 개발 test 구성과 배포 구성이 문서로 분리돼야 함 |
| "조정 서버가 외부에 있는 걸 어떻게 설명하나" | 조정 서버는 개발 test 단계에만 관여, 운영 배포에는 관여하지 않음 | **완화.** 단, 설치 절차서에 "test용 Tailscale 흔적(클라이언트·키·경로)이 운영 전환 시 제거된다"는 확인이 필요(잔존 조건) |
| "SSL VPN 접속이 내부망으로 판별되는지 불명" | 내부망 대역(CIDR)을 관리자가 등록, 회사 VPN/전용회선(MPLS) 대역을 내부망으로 등록 가능 | **부분 완화·검증 필요.** 명세 1.1의 회사 대역 인정과 일치 방향이나, **당사 SSL VPN 경로가 실제로 `INTERNAL`로 판별되는지는 필수 조건 4번·붙임 2의 3·4번 시험으로 그대로 확인** |

- Tailscale이 운영 경로에서 빠지면서 1차 공문 "우려 5번"의 심각도는 내려감. 그러나 **보안 심의 자체는 유지**함. 심의 대상이 "외부 조정 서버 통신"에서 "웹 서비스↔실행기 mTLS 구성과 내부망 대역 설정, test 구성 잔존 여부"로 **바뀐 것**으로 봄
- 1차 공문 제출 요청 3번(실행기 구성도·Tailscale 조정 서버 통신 범위)은 **"개발 test 구성과 운영 배포 구성 두 가지를 구분한 구성도"**로 바꿔 다시 요구함

### 1.5 SSL VPN 내부망 판별 재평가 (필수 조건 4번 유지)

- 업체 설명으로 "회사 VPN/전용회선(MPLS) 대역을 내부망으로 등록 가능"이 확인되는 방향이나, **필수 조건 4번(당사 SSL VPN 접속의 내부망 판별)과 그 검수 시험(붙임 2의 3·4번)은 그대로 유지**함
- 이유: SSL VPN은 종단 IP가 VPN 게이트웨이 대역으로 나타나는지, 스플릿 터널링 설정에 따라 실제 출발지 대역이 달라지는지가 환경마다 다름. "등록 가능"이 "당사 경로에서 실제로 `INTERNAL`로 판별됨"을 보장하지 않음
- 하승우 대리 야간 시나리오(집에서 SSL VPN 접속 후 `DEPLOY` 승인)를 파일럿 2·3주차 야간 시나리오에 그대로 넣음. 외부망 배포 차단(4.4)은 유지

## 2. 논의 내용

### 2.1 실행기가 "무거운 러너"가 아니라는 설명을 어떻게 받을 것인가

- 노경태: 업체가 보내온 보완 설명을 보니 실행기가 별도의 무거운 서버가 아니라 검증하고 복호화하고 웹쉘 여는 가벼운 컴포넌트라고 한다. 그러면 2대니 서버 사양이니 하는 말을 접고, 비용도 내려야 하는 것 아니냐고 물음
- 차선영: 경량이라는 건 서버 비용 이야기일 뿐이고, 그 컴포넌트가 죽으면 6개 센터 긴급 변경이 멈춘다는 사실은 그대로임. 가용성과 서버 무게는 분리해야 한다고 지적
- 결론: 1.2대로 성격은 재기술하되 가용성 요구는 유지. "서버 2대"라는 표현을 "컴포넌트 다중화/페일오버"로 바꿈(1.3)

### 2.2 E2EE 설명이 "반대 사유"를 지우는가

- 노경태: 업체가 승인 envelope을 실행기 공개키로만 열고 웹 서비스는 못 연다고 했으니, 차 팀장이 말한 반대 사유 하나가 사라진 것 아니냐고 물음
- 차선영: 명세 2.4·4.5와 같은 방향이라 반가운 설명이지만, 설명은 설명이고 파일럿에서 변조·재사용 시험(붙임 2의 5·6번)으로 실제로 확인해야 함. 웹 서비스 측 Plan을 변조하면 `PLAN_HASH_MISMATCH`, 같은 envelope을 재전송하면 `NONCE_ALREADY_USED`로 막히는 걸 직접 봐야 수용한다고 함
- 결론: 1.2대로 설명 접수, 검수 시험표 유지

### 2.3 "서버 2대"를 "다중화"로 바꾸면 협상 카드가 약해지는가

- 노경태: 2대 구성이라고 하면 구축비 1,500만 원 안에 넣으라고 밀 수 있었는데, 다중화라고 두루뭉술하게 쓰면 업체가 "구성은 저희가 알아서"라며 빠져나갈까 걱정된다고 함
- 차선영: 대수를 못 박는 대신 결과(전환 시간, 상태 이전, 중복 실행 방지, 복호화 키 처리)를 서면으로 받으면 오히려 검수가 분명해진다고 함. 경량 컴포넌트라도 실행기 개인키와 nonce 소진 상태가 예비 쪽에 안 이어지면 전환해도 무용지물이라는 점을 짚음
- 노경태: 그러면 "다중화하되 상태 이전·중복 실행 방지·복호화 키를 서면으로, 구성하면 구축비 포함"으로 쓰자고 정리. 숫자 대신 조건을 계약서에 박는 방식은 본인 방식과 맞다고 함
- 결론: 1.3 표대로 서면 확인 요구

### 2.4 Tailscale이 개발 test용이라는 설명의 효과

- 노경태: 업체가 Tailscale은 개발 test용이고 운영 배포는 우리 내부망 mTLS라고 했다. 그러면 외부 조정 서버 심의 문제는 없어진 것 아니냐고 물음
- 차선영: 운영 경로에서 조정 서버가 빠지는 건 큰 완화가 맞다. 하지만 보안 심의가 사라지는 게 아니라 심의 대상이 바뀐 것임. test 단계에서 깔린 Tailscale 클라이언트·키·경로가 운영 전환 때 실제로 제거되는지, 웹 서비스↔실행기 mTLS 구성과 내부망 대역 설정이 심의 대상이 된다고 함
- 노경태: 그럼 공문에는 "완화됐다"가 아니라 "완화된 부분"과 "그래도 확인할 부분"을 나눠 쓰자고 함
- 결론: 1.4대로 완화/잔존 구분, 제출 요청의 구성도를 "test 구성·운영 구성 두 가지"로 바꿈

### 2.5 SSL VPN 판별은 설명으로 끝낼 수 있는가

- 노경태: 업체가 회사 VPN·전용회선 대역을 내부망으로 등록할 수 있다고 했으니, 필수 조건 4번도 완화로 처리하면 질의가 하나 줄지 않느냐고 함
- 차선영: 안 된다고 분명히 함. SSL VPN은 스플릿 터널링이나 게이트웨이 대역 때문에 실제 출발지 대역이 환경마다 다르고, "등록 가능"이 "우리 경로에서 `INTERNAL`로 판별됨"을 보장하지 않음. 새벽 세 시에 하승우 대리가 집에서 붙었을 때 배포 승인이 되는지는 파일럿에서 직접 봐야 한다고 함
- 노경태: 그러면 4번은 건드리지 말고 그대로 두자고 수긍. 설명으로 필수 조건을 빼면 나중에 감사에서 "검증 안 했다"는 말이 나온다는 점에도 동의
- 결론: 1.5대로 필수 조건 4번·붙임 2의 3·4번 유지

### 2.6 2차 공문을 새 공문으로 낼지, 회신 안에 녹일지

- 노경태: 11월 13일(금) 업체 1차 회신이 오는데, 그때 2차 공문을 따로 낼지 회신 검토 안에 녹일지 물음. 문서가 많아지면 결재선만 복잡해진다고 함
- 차선영: 실행기 성격과 Tailscale은 1차 공문 우려·요청의 "재정의"라서, 1차 공문을 인용하고 변경분만 쓰는 2차 공문 한 장이 감사 추적에 낫다고 함. 필수 조건과 검수 시험표는 다시 쓰지 말고 1차 공문을 참조로 걸자고 함
- 결론: 1.6대로 제2026-0415호, 변경분만 기재, 필수 조건·붙임은 1차 공문 인용

### 2.7 보안 심의 범위 조정

- 노경태: Tailscale이 운영에서 빠지면 심의가 가벼워질 테니, 11월 20일(금) 안에 끝날 가능성이 커진 것 아니냐고 함. 그러면 지연 규칙도 느슨하게 갈 수 있지 않느냐고 물음
- 차선영: 심의가 가벼워질 수는 있지만 완료 날짜를 지금 당겨 약속할 수는 없다고 함. 심의 대상이 바뀌었다는 걸 담당자에게 재공유해 범위 조정은 요청하되, 11월 20일(금) 완료를 전제로 품의·계약을 당기지는 않겠다고 함. 지연 규칙(11월 30일 재보류)은 그대로 둠
- 결론: 1.7대로. 심의 범위 조정 요청은 하되 일정 전제는 바꾸지 않음

### 2.8 경량 컴포넌트라는 설명이 비용 인하 근거가 되는가

- 노경태: 업체가 경량이라고 했으니 구축비나 서버 사양 비용을 더 깎을 명분이 생긴 것 아니냐고 함
- 차선영: 서버 하드웨어 비용은 내려갈 수 있어도 다중화·페일오버·야간 지원 비용은 그대로 들어간다고 함. 경량이라서 싸다는 논리로 가용성 요구를 깎으면 9월 사고 때처럼 새벽에 멈춘다는 점을 지적
- 노경태: 그럼 구축비는 다중화 포함 조건으로 1,500만 원을 그대로 밀고, 경량이라는 건 서버 사양 견적을 낮추는 근거로만 쓰자고 정리
- 결론: 비용은 다중화 포함 기준 유지, 경량은 서버 사양 산정에만 반영
