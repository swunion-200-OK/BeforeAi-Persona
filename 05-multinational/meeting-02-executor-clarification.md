## 1. 결정 사항

### 1.1 업체 보완 설명의 지위

- 업체가 2026-11-10(화) 1차 자료(`letter-01` 8항 1~8번)를 기한 안에 회신하면서 두 가지 **보완 설명(clarification)**을 함께 보냄
  - 보완 1: 실행기는 별도 인프라 러너가 아니라 **경량 컴포넌트**다 — (a) Plan 해시를 실행기가 자체 생성하고 Ed25519 서명·nonce를 검증하는 "서명 검증기", (b) 승인 envelope을 비대칭키 E2EE로 받아 **실행기 공개키로만** 복호화(웹 서비스는 열지 못함), (c) 검증 6단계 통과 시 웹쉘 세션으로 로컬 작업을 수행
  - 보완 2: 명세 1.1·5장의 **Tailscale은 개발·테스트 단계의 임시 구성**이며, 운영 배포는 고객사 내부망 연결(웹 서비스↔실행기 **mTLS**, 내부망 대역은 고객사 관리자가 설정, 사무소별 대역 등록 가능)이다
- 두 설명 모두 **메일 본문과 아키텍처 문서 개정본(rev B)로 서면 수령**함. 구두·메신저 설명이 아니므로 검토에 반영함 (차유나 원칙 충족)
- 단, 보완 설명은 **현재 명세(API 명세서)를 대체하지 않음**. 명세 1.1·5장 본문과 다르면 업체가 명세/문서를 어느 판으로 계약 기준으로 삼을지 서면으로 확정해야 함 (할 일)

### 1.4 그대로 **남는** 필수·본사 요구 (보완 설명으로 바뀌지 않음)

- **본사 VRM Tier 1 승인** (파일럿 범위 VRM 승인). 보완 설명은 네트워크·실행기 구조에 관한 것이고 VRM 분류·승인 틀은 그대로
- **SOC 2 Type II 또는 ISO 27001** (미보유 시 보완 패키지는 Global VRM 서면 예외 승인 대상)
- **DPA·데이터 저장 리전**: 보완 1에서 웹 서비스가 envelope을 못 연다는 점은 좋으나, 감사 로그에 남는 직원 이름·사번·IP, 그리고 **AI 분석 시 소스코드·프롬프트의 외부 전송 경로·리전·보관/학습 정책**은 그대로 확인 대상. E2EE는 "AI 분석으로 코드가 어디로 가는가"를 대체하지 않음
- **Okta SSO (SAML/OIDC)·SCIM**: 명세 3.1은 여전히 사번·비밀번호. 보완 설명과 무관하게 남음
- **영어 UI·영어 오류 메시지** (1.2 `message`): 글로벌 조건으로 그대로
- **ServiceNow CHG·실행 창을 Plan 해시에 넣고 실행기가 실행 직전 검사 / GitHub Enterprise Cloud 접근 방식 공개·보호 브랜치 시험**: 한국 확대 필수 그대로
- **EAR 수출통제**: EAR 통제 기술 데이터의 외부(AI 분석) 전송 금지는 보완 설명과 무관하게 유지. E2EE로 전달되는 것은 승인 envelope이지 AI 분석 입력이 아님

### 1.5 결론 틀 유지

- 공문 결론 틀은 그대로: **한국 법인 한정 Limited Pilot, 본사 VRM 승인 후 착수**. 정식 채택·구매 약정·글로벌 확대 약속 아님
- 보완 설명 2건으로 **착수 조건 ③에서 Tailscale 예외가 빠지고 ⑥(대체 네트워크 구성 질의)이 해소**되는 것이지, 착수 조건 ①(VRM 승인)·②(Pilot Agreement)·④(필요 시 ARB)는 유지
- 후속 공문(`letter-02-to-vendor.md`, NBK-PROC-2026-1112-02)으로 ① 실행기 성격 재정의 수용과 ② Tailscale 완화를 알리고, 남는 필수·본사 요구를 구분해 다시 통지

### 1.6 VRM 접수(11/11) 반영

- 차유나는 11/11 VRM Limited Pilot 접수 시, 접수서에 **"업체 보완 설명으로 네트워크 구성은 내부망 mTLS로 변경, Tailscale 상시 예외 불요"**를 한 줄로 명시하고 아키텍처 문서 rev B를 첨부
- Rachel Stein에게는 "실행기 경량 컴포넌트·E2EE" 설명이 **격리 랩·합성 데이터 한정 파일럿 판정을 바꾸지는 않음**을 먼저 밝힘. 보완 설명으로 VRM 범위를 넓히지 않음

## 2. 논의 내용

### 2.1 실행기가 "서버"인가 "컴포넌트"인가

- 권대현: letter-01 6항 11번(실행기 단일 구성)과 붙임의 이중화 요구를 업체가 "서버 2대"로 읽고 실행기 연간 라이선스 2배 견적을 냈는데, 보완 1을 보면 실행기는 경량 검증·복호화·웹쉘 실행 컴포넌트라 "서버 대수"가 아니라 "컴포넌트 다중화·페일오버"로 물어야 한다고 봄
- 차유나: 재서술은 받아들이되, 비용 영향이 바뀌므로 견적서에 "실행기 비용"을 **컴포넌트 라이선스/HA 구성 기준**으로 다시 받기로 함. 단일 실행기 장애 시 상태 유지(4.3 `502 EXECUTOR_UNAVAILABLE`)와 복구 시간은 파일럿에서 여전히 검증

### 2.2 E2EE가 DPA·EAR를 대체하는가

- 권대현: 웹 서비스가 envelope을 못 연다는 점은 "중간 경로 위조 불가"를 확실히 하지만, 그건 승인 전달 경로 얘기지 AI 분석 입력 얘기가 아님
- 차유나: 바로 그 구분을 공문에 쓰겠다고 함. E2EE는 letter-01 4항 2번의 강화 근거일 뿐, 5항 2번(DPA·리전·AI 분석 전송)과 6항 EAR 요구를 내리지 않음. "암호화돼서 보낸다"와 "코드가 외부 AI로 안 나간다"는 다른 문장

### 2.3 Tailscale 예외를 착수 조건에서 뺄 수 있는가

- 차유나: meeting-01에서 가장 걱정한 게 Tailscale 예외였음(페르소나 11, 사내 표준 아님·예외 승인 경험 없음). 배포가 내부망 mTLS면 **"표준 외 도구 상시 사용"이 아니므로 예외 승인 대상 자체가 아님**
- 권대현: 다만 개발 test 단계에서 업체가 Tailscale을 쓸 수 있으니, 설치 때 그 트래픽이 격리 랩 VLAN을 벗어나지 않는지는 확인해야 한다고 보탬. 상시 예외는 빼되 설치 점검 항목으로 남김
- 남기훈(참석): mTLS·사무소별 대역 등록 방식이면 Zscaler와 분리된 격리 랩 VLAN에서 돌릴 수 있고, Tailscale 상시 예외 서류는 필요 없다고 확인. 11/13 판단 항목을 "Tailscale 예외"에서 "mTLS·격리 VLAN 구성"으로 바꾸기로 함

### 2.4 보완 설명이 일정을 당기는가

- 권대현: Tailscale 예외가 빠지면 11/13 보안 판단이 가벼워져 11/23 시작 목표가 더 단단해지지 않느냐고 물음
- 차유나: 판단 항목이 바뀌어 **불확실성은 줄지만 VRM 판정(목표 11/18)과 Pilot Agreement는 그대로**라 시작일을 더 당기지는 않음. 11/23은 여전히 승인 조건부 목표이고, 자동으로 앞당기지 않음(meeting-01 일정 규칙 유지)

### 2.5 명세와 보완 설명의 불일치

- 차유나: 명세 1.1은 Tailscale 100.64.0.0/10을 내부망으로, 5장은 Tailscale 기반 연결을 기술하는데 보완 설명은 "개발 test용, 배포는 mTLS"라고 함. 계약 시 어느 판을 기준으로 삼는지 서면 확정이 없으면 나중에 분쟁이 됨
- 권대현: 동의. 업체에 "명세 개정판(rev)과 아키텍처 문서 중 계약 기준 문서를 명시하고, 1.1·5장 Tailscale 기술을 배포 기준으로 갱신해 달라"를 요청하기로 함
