4. 보완 설명에 대한 우리 학교의 이해 (귀사 확인 요청)

   아래는 보완 설명을 우리 학교가 이해한 내용입니다. 사실과 다른 부분이 있으면 회신에 바로잡아 주십시오.

   **가. 실행기의 성격 (보완 설명 1)**

   | 번호 | 우리 학교가 이해한 내용 | 확인 요청 |
   | --- | --- | --- |
   | 1 | 실행기는 무거운 별도 인프라 러너가 아니라, 다음 기능을 수행하는 **경량 컴포넌트**임 | 맞는지 가/부로 회신 |
   | 2 | (가) Plan 해시를 실행기가 직접 생성하고, Ed25519 서명과 1회용 nonce를 검증하는 "서명 검증기" | 2.3, 2.4, 5장과 일치하는지 |
   | 3 | (나) 승인 envelope을 비대칭키 종단간 암호화(E2EE)로 수신하여 **실행기 공개키로만 복호화**하며, 웹 서비스는 해당 envelope을 복호화할 수 없음 | 복호화 키의 보관 위치와 생성 주체 포함 회신 |
   | 4 | (다) 검증 6단계를 모두 통과한 경우에만 웹쉘 세션으로 로컬 작업을 수행 | 5.1 6단계 중 하나라도 실패 시 웹쉘 미개방 여부 |

   **나. Tailscale 및 운영 네트워크 구성 (보완 설명 2)**

   | 번호 | 우리 학교가 이해한 내용 | 확인 요청 |
   | --- | --- | --- |
   | 1 | Tailscale은 귀사의 **개발·테스트 단계 임시 구성**이며, 운영 배포에는 사용하지 않음 | 맞는지 가/부로 회신 |
   | 2 | 운영 배포는 **교내 내부망(실습망) 연결**이며, 웹 서비스와 실행기 사이는 mTLS로 연결됨 | mTLS 상호 인증 방식과 인증서 발급·갱신·폐기 주체 회신 |
   | 3 | 내부망 대역은 **학교 관리자**가 설정하며, 실행기(및 운영에 필요한 구성요소)를 교내 실습망에 **내부 설치형**으로 둘 수 있음 | 내부 설치형 운영이 가능한지, 필요한 구성요소 목록 회신 |
   | 4 | 우리 학교 실습망은 교육청 업무망·교내 인터넷망과 분리 운영됨 | 분리망 환경에서 운영 시 외부 오버레이 네트워크의 상시 사용 여부(상시 사용 시 사유) |

5. 재검토 결과 — 완화 항목과 잔존 조건의 구분

   보완 설명으로 우려가 줄어든 항목(완화)과, 보완 설명으로도 풀리지 않아 그대로 유효한 조건(잔존)을 구분합니다. **완화 항목도 1단계 시범의 실제 설치·동작으로 확인하기 전까지는 요구서·운영안에 단정하지 않습니다.**

   **가. 완화 항목 (보완 설명 수용)**

   | 번호 | 기존 우려 (관련 가 공문) | 보완 설명으로 완화된 내용 | 단서 |
   | --- | --- | --- | --- |
   | 1 | 실행기 서버 증설 부담 (별도 과목 약 450만 원 가정) | 경량 컴포넌트로 확인되어 기존 실습 서버(`hanbit-lab-04`) 활용 가능성이 높아짐. 신규 서버 구매 가정은 **보류**(미구매 가능성 포함) | 권장 사양·설치 시간·여유 자원 1단계 검증 전제 |
   | 2 | 전담 인프라 인력 부담 (학교는 전담 인력이 약하고 실습망 자원 한정) | 경량 컴포넌트는 설치·운영 부담이 낮아 학교 여건에 유리 | "경량이라 관리 불필요"로 보지 않음. 기술 책임자·업체 지원 범위는 운영 문서에 명기 |
   | 3 | 실행기 단일 구성, 장애 시 수업 중단 (가 공문 마. 13번) | 우리 학교는 이중화(HA)를 요구하지 않음. **페일오버 관점**(재기동 시간·상태 유지·복구·대체 수업 절차)으로 전환 | `502 EXECUTOR_UNAVAILABLE` 뒤 요청 상태 불변은 1단계 시험 항목으로 유지 |
   | 4 | 운영 시 Tailscale 상시 의존 우려 | 운영은 교내 실습망 mTLS 내부 설치형. Tailscale은 개발·테스트 임시 구성 | 운영 구성도와 4항 나. 확인 결과로 최종 판단 |

   **나. 잔존 조건 (보완 설명으로 풀리지 않음. 관련 가 공문 그대로 유효)**

   | --- | --- | --- | --- |
   | 1 | 학생 개인정보 수집 항목·저장 위치·AI 외부 전송·보관·파기 | **E2EE는 승인 envelope만 보호함.** 웹 서비스가 저장하는 계정·프롬프트·Plan 본문·실행 로그는 별개 | 가 6항 4·5번, 명세 2.1, 1.1, 4.8 |
   | 2 | 웹 서비스 자체의 운영 위치와 보안 인증 | 실행기가 교내에 있다고 웹 서비스도 교내에 있는 것이 아님 | 가 6항 3번, 명세 1.1 |
   | 3 | 승인 자격 구분 (학생 승인 배제, 기간제 교사 키 처리) | 역할이 `EMPLOYEE` 공통. 학생·교사·기간제 구분이 실행기 로컬 정책까지 반영되는지 | 가 5항 가-1·가-4, 명세 1.3, 2.2 |
   | 4 | 계정·서명 키 대량 관리 (신입생·졸업생 각 약 160명, 기간제 계약 종료) | 계정·키 처리 API가 모두 단건 | 가 5항 나-1, 명세 3.2 |
   | 5 | 감사 로그 내보내기·인쇄, 조회 전용 권한, 평가·생활기록부 미사용 | 현재 조회만 가능, 조회 전용 역할 없음 | 가 5항 가-5·가-6, 명세 3.9, 4.8 |

6. 추가 요청 자료 (관련 가 공문 제출 자료에 더하여, 같은 기한 2026. 11. 13.(금)까지)

   | --- | --- | --- |
   | 1 | 운영 네트워크 구성도 | 개발·테스트(Tailscale)와 운영(교내 실습망 mTLS 내부 설치형)을 구분하여 표기. 웹 서비스↔실행기 연결 경로, 외부 네트워크 사용 구간, 내부망 대역 설정 주체 포함 |
   | 2 | mTLS 인증서 운영 방안 | 상호 인증 방식, 인증서 발급·갱신·폐기 주체(학교/업체)와 절차. 우리 학교 실습망 분리 환경 적용 가능 여부 |

   | 5 | E2EE 복호화 키 관리 | 실행기 공개키·개인키 생성 주체와 보관 위치, 키 교체 절차. 웹 서비스가 승인 envelope을 복호화할 수 없음을 보이는 설명 또는 시험 방법 |
   | 6 | 운영 시 외부 전송 구간 명세 | 운영 구성에서 학생 개인정보·프롬프트·Plan·로그가 교내 밖(외부 클라우드·외부 AI 제공업체)으로 나가는 구간이 있는지. 있다면 대상·항목·목적 (E2EE 설명과 별개로, 가 공문 제출 자료 4번 보강) |
