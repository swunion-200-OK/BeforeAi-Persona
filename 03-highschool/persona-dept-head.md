> "AI 쓰지 말라고 하면 애들은 집에 가서 몰래 씁니다. 저는 애들이 Plan을 읽고, 위험한 줄 알고, 선생님 승인을 받아서 실행하는 그 과정 자체를 가르치고 싶어요. 회사 가면 매일 하는 일이거든요."

같은 학교 행정실장 페르소나는 `persona-admin-chief.md`에 있습니다.

## 2. MBTI와 성향

### 2.1 INTJ 특징이 드러나는 모습

- **내향(I)**: 교무실보다 실습실 준비실에 있는 시간이 김. 회의에서는 듣다가 마지막에 정리안을 내놓음
- **직관(N)**: "이 학생들이 3년 뒤 회사에서 뭘 하게 될까"부터 생각함. 교육과정도 그 기준으로 짬
- **사고(T)**: 학생 실수를 혼내기보다 "왜 그게 가능했는지"를 먼저 따짐. 10월 사고 때도 학생 징계를 반대함
- **판단(J)**: 학기 시작 전에 16주 수업 계획을 주차별로 다 짜 둠. 계획이 밀리면 주말에 보충 자료를 만듦

### 2.2 MBTI를 대하는 태도

- 학생들이 "선생님 MBTI 뭐예요?"라고 물어서 검사함. INTJ가 나오자 학생들이 "역시"라고 함
- 노상규 실장이 ESTJ라는 이야기를 듣고 "규정 먼저인 분이니 규정부터 들고 가자"고 전략을 바꿈
- 팀 프로젝트 조 편성에 MBTI를 쓰자는 신규 교사 제안에는 반대. "역할은 실력과 관심으로 나눠요"

### 2.3 성격 요약

| 강점 | 약점 |
| --- | --- |
| 실무 경험이 있어 학생들에게 "회사에서는 이렇게 해"를 구체적으로 보여 줌 | 행정 절차를 "개발 일정 막는 일"처럼 느껴 표정에 드러남 |
| 시스템을 잘 봄. 사고가 나면 사람보다 구조를 먼저 고침 | 혼자 고치는 게 빨라서 일을 넘기지 못함. 사고 복구도 이틀 밤을 혼자 샘 |
| 학생을 믿음. 실수한 학생에게 다시 기회를 줌 | 학생을 믿는 만큼 학생의 판단 범위를 넓게 잡는 편 |
| 근거를 정리함. 회의 전에 자료를 한 장으로 만들어 감 | 기술 용어를 줄이지 못해 비전공자가 따라오기 어려워함 |
| 약속한 날짜를 지킴 | 일정이 막히면 말이 짧아지고 대안을 너무 빨리 여러 개 내놓음 |

### 2.4 스트레스 반응

- 서버 장애나 학생 사고가 나면 오히려 침착해지고, 끝난 뒤에 몸살이 남
- 회의가 결론 없이 길어지면 노트에 결정 항목을 미리 적어 놓고 "이거 셋만 정하면 될 것 같아요"라고 말함
- 주말에 아들과 보드게임을 하거나 혼자 한강 자전거길을 2시간 달리며 풂

### 2.5 의사결정 스타일

1. 사고가 다시 일어날 수 있는 경로를 모두 적는다 (10월 사고 때 7개를 적음)
2. 막을 수 있는 것과 교육으로 줄일 것을 나눈다
3. 학생 입장에서 불편이 얼마나 생기는지 시간으로 잰다 ("승인 기다리다 수업 끝나면 안 돼요")
4. 작게 시범하고 숫자를 모은다
5. 결과가 나쁘면 계획을 바꾸는 데 주저하지 않는다

## 4. 성장 배경과 경력

### 4.1 어린 시절과 학창 시절

- 대전에서 1남 1녀 중 장녀로 자람. 연구단지 근처라 친구 부모님 중 연구원이 많았음
- 중학교 때 컴퓨터 학원에서 베이직을 배우고, 고등학교 정보 선생님이 운영한 홈페이지 동아리에서 처음 웹사이트를 만듦
- 그 정보 선생님이 "넌 개발도 하고 가르치기도 할 사람"이라고 한 말이 교사가 된 이유 중 하나
- 대학 때 교직 이수를 해 두었고, 졸업 후에는 개발자로 먼저 일하기로 함

### 4.3 기억에 남는 성공과 실패

**목격: 2013년 회사 운영 DB 사고**
- 옆 팀 동료가 운영 DB에서 테스트 데이터를 지우려다 조건문 없이 실행해 주문 테이블 일부가 지워짐
- 복구에 9시간, 고객 공지까지 나감. 동료는 회사를 떠남
- 회사는 그 뒤 "운영 DB 쿼리는 두 사람이 보고 승인"하는 절차를 만듦. 은하는 그 절차를 처음 설계한 팀원 중 한 명
- 지금도 학생들에게 이 이야기를 함. "그 사람이 나빠서가 아니라 혼자 실행할 수 있어서 사고가 난 거야"

**성공: 2023년 지방기능경기대회 웹 디자인 및 개발 직종 금상 지도**
- 학생 2명이 금상, 1명이 은상. 학교 홍보 현수막에 은하 이름이 올라감
- 연습 때 학생들에게 배포 전 체크리스트를 쓰게 한 것이 대회 실수 0건으로 이어졌다고 믿음

**실패와 사고: 2026년 10월 13일(화) 실습 서버 DB 삭제**
- 6교시 "웹 프로그래밍" 시간, 2학년 2반 한 팀이 AI 에이전트에게 "테스트 DB를 깨끗하게 초기화하는 스크립트"를 만들게 함
- 팀 계정으로는 권한이 부족해 실패하자, 학생 한 명이 서버 설정 파일에서 2022년 전임 교사가 남긴 공용 MySQL 관리자 비밀번호를 찾아 스크립트에 넣음
- 스크립트는 시스템 DB를 뺀 모든 DB를 지우는 구조였고, 실습 서버 `hanbit-lab-02`의 DB 17개가 삭제됨
  - 3학년 졸업 작품 팀 DB 11개, 2학년 팀 DB 5개, 동아리 Byte의 급식 알림 앱 "오늘밥" DB 1개
- 백업은 주 1회(일요일)라 10월 11일(일) 백업으로 복구. 10월 12일(월)~13일(화) 이틀치 작업이 사라짐
- "오늘밥" 알림은 10월 13일 저녁부터 15일 아침까지 멈춤. 사용 학생 312명
- 은하는 이틀 밤을 학교에서 새우며 복구함. 학생 징계는 하지 않기로 교장과 합의
- "오늘밥" DB에 학번·이름·알레르기 항목이 있었던 것을 노상규 실장이 이때 처음 알게 됨. 은하도 동아리 앱에 그 정도 정보가 들어 있는 줄은 정확히 몰랐음을 인정함

## 10. 본 서비스 도입 검토

### 10.1 은하가 정의한 문제

- 학생이 AI로 만든 작업 중 DB·배포·데이터 수정처럼 다른 팀에 영향을 줄 수 있는 것은 교사가 내용을 보고 서명한 것만 실행되어야 한다
- 학생에게는 서버 관리자 비밀번호가 보이지 않아야 한다 (실행기가 대신 실행)
- 문서 작성이나 작은 코드 수정은 수업 시간 안에 끝날 만큼 빨라야 한다 (요청부터 실행까지 5분 이내 목표)
- 승인 과정이 학생에게 "Plan을 읽고 위험도를 이해하는" 학습이 되어야 한다

### 10.2 선택지 비교 (교장 보고 자료)

| 선택지 | 비용 | 장점 | 단점 |
| --- | --- | --- | --- |
| 본 서비스 | 업체 견적 대기 (데모 때 구두로 사용자당 월 9,000원, 교육기관 절반 검토) | 승인·서명·감사·킬 스위치가 이미 있음. 학생에게 관리자 권한을 줄 필요가 없음 | 학생 계정·키 운영, 외부망 숙제 제한, 학교 계약 절차 |

| 분석 재시도 제한 | 3회 넘으면 `409 RETRY_LIMIT` | 3.5, 1.2 | "프롬프트를 못 쓰는 학생은 금방 막혀요. 그건 교육적으로 나쁘지 않지만 다음 단계 안내가 필요해요" |
| 서명 만료 없음 | 승인 서명에 만료 항목 없음 | 2.4 | "방학 전에 반쯤 승인된 요청이 3월에 마저 승인되면 그대로 실행되나요? 학기말 일괄 취소가 필요해요" |
| 알림 | 알림은 Slack만 | 3.1 `/me/notification-settings`, 3.2 `/admin/integrations/slack` | "학교는 Slack을 안 씁니다. 메일이나 웹훅이라도 있어야 교사가 승인 요청을 알아요" |
| 감사 로그 열람 범위 | `DEPT_MANAGER`는 소속 부서 전체 로그 열람 | 3.9 | "제가 학과 학생 240명 행동 기록을 다 보게 돼요. 평가에 쓰라는 압력이 올 거예요" |
| 계정 일괄 처리 없음 | 계정 생성·비활성화·키 폐기가 모두 단건 | 3.2 | "3월 신입생 160명, 2월 졸업생 160명을 한 명씩요?" |
| 로그인 ID | 사번·비밀번호 로그인 | 3.1 `POST /auth/login` | "학번을 쓰면 개인정보예요. 임의 ID를 써도 되나요?" |
| 실행기 단일 구성 | 연결 실패 시 `502 EXECUTOR_UNAVAILABLE`, 상태 유지 | 4.3, 5장 | "실행기 서버가 죽으면 그 시간 실습이 전부 멈춰요. 수업 대체 방법이 있어야 해요" |
| 역할이 셋뿐 | `ADMIN`·`DEPT_MANAGER`·`EMPLOYEE` | 1.3 | "교사와 학생이 같은 `EMPLOYEE`예요. 학생을 승인권자에서 빼는 표시가 필요해요" |

### 10.5 은하가 생각한 승인 기준 (시범안)

| 작업 유형 | 기본 위험도 | 은하의 시범안 | 이유 |
| --- | --- | --- | --- |
| DOC | LOW | 담당 교사 1명 (본인 승인 없음) | 학생 키를 만들지 않기 위해 |
| CODE_MINOR | LOW | 담당 교사 1명 | 같은 이유. 단 대기 시간을 측정 |
| CODE_FEATURE | MEDIUM | 담당 교사 1명 | |
| DATA_READ | MEDIUM | 담당 교사 1명 | |
| DATA_WRITE | HIGH | 담당 교사 1명 + 학과부장 | 다른 팀에 영향 |
| DB | HIGH | 담당 교사 1명 + 학과부장 | 10월 사고 유형 |
| DEPLOY | HIGH | 담당 교사 1명 + 학과부장 | 교내 서비스("오늘밥") 배포 포함 |
| 금지 | FORBIDDEN | `DROP DATABASE`, 다른 팀 스키마 접근, 실습망 밖 접속, 공용 계정 사용 | |

- 은하는 원래 동아리 3학년 학생끼리 DOC·CODE_MINOR를 서로 승인하는 실습(`SAME_DEPT_OTHER`)을 넣고 싶었음. 학생 키가 필요하고 부서 단위 문제가 있어 보류 쪽으로 기울어 있음
- HIGH 작업에 학과부장이 매번 들어가면 은하가 병목이 된다는 걸 본인도 앎

### 10.6 시범 사용 계획 (은하가 작성한 초안)

| 주차 | 내용 | 측정 지표 |
| --- | --- | --- |
| 준비 | 실행기를 실습망 서버(`hanbit-lab-04`)에 설치, 교사 키 등록, 가명 학생 계정 생성 | 설치 시간, 교사 키 등록 완료율 |
| 1주 | 2학년 2반·3반 웹 프로그래밍 수업에서 DOC·CODE 작업만 | 요청~실행 시간, 교사 승인 건수 |
| 2주 | DB·DATA 작업 추가. 금지 규칙 시험 | `FORBIDDEN_TASK` 차단 건수, 교사 승인 대기 시간 |
| 3주 | 동아리 Byte "오늘밥" 배포를 본 서비스로 | 배포 승인 시간, 킬 스위치 시험 |
| 4주 | 일부러 깨 보기 (Plan 변조, 서명 재사용, 실행기 연결 끊기) | `PLAN_HASH_MISMATCH`, `NONCE_ALREADY_USED`, `502 EXECUTOR_UNAVAILABLE` 확인 |
| 종료 | 학생·교사 설문 (평가와 무관함을 사전 고지) | 수업 시간 내 완료율, "계속 쓰고 싶다" 비율 |

### 10.7 성공 기준

- DB·DATA_WRITE·DEPLOY 작업 100%가 교사 서명 후 실행됨
- LOW 작업 요청부터 실행까지 중앙값 5분 이내
- 50분 수업 안에 계획한 실습을 끝낸 팀 비율 80% 이상
- 교사 1인당 하루 승인 처리 시간이 현재 임시 체계(약 60분)보다 줄어듦
- 학생에게 서버 관리자 비밀번호가 보이는 경로 0개

## 11. 고민과 불안

- **교사 업무량**: 승인 버튼을 누르는 사람이 결국 교사. 지금 임시 체계보다 덜 힘들어야 동료들이 받아들임
- **학생 개인정보**: 미성년 학생의 이름·학번이 외부 서버에 저장되는 문제. 사고 때 알레르기 정보 일을 겪고 더 신경 씀
- **감사 로그 오용**: 담임이나 학부모가 "우리 애 실수 기록"을 보자고 하거나, 수행평가 근거로 쓰자는 말이 나올까 걱정
- **외부망 숙제**: 시범 학급 학생 대부분이 집에서 과제를 함. 막히면 개인 무료 AI 계정으로 다시 우회할 것
- **학과 형평성**: 인공지능과도 같은 위험이 있는데 소프트웨어개발과만 쓰면 변경미 부장과 사이가 어색해짐
- **행정 일정**: 노상규 실장이 말하는 보안성 검토·학교장터·학운위 일정이 길게 느껴짐. 그동안 임시 체계로 버텨야 함
- **본인 이탈 위험**: 2027년 3월이 은하의 한빛고 6년 차 끝이라 전보 대상. 떠나면 누가 운영하나

## 13. 커뮤니케이션 방식

### 13.1 업체를 대할 때

- 데모 첫 10분 안에 API 명세를 요청함. 데모 전날 명세를 다 읽고 질문 15개를 준비함
- "다음 버전에 됩니다"에는 "어느 학기 안에요?"라고 되물음. 학교는 학기 단위로 움직이기 때문
- 영업 담당보다 개발자와 직접 이야기하길 원함
- 보안 설명이 명세와 다르면 그 자리에서 절 번호를 들어 바로잡음

### 13.2 학교 안에서

- 비전공 교사에게는 "회사에서는 이렇게 해요"를 먼저 말하고 기술 설명은 뒤로 미룸
- 교장 보고는 사고 경위, 재발 방지 구조, 필요한 예산 순서로 한 장
- 학생에게는 "왜 막혔는지"를 오류 코드와 함께 보여 줌. "`403 NOT_APPROVER`는 네가 승인권자가 아니라는 뜻이야"

### 13.3 노상규 실장과의 관계

- 사고 다음 날 "백업 장비부터 사 주세요"라고 갔다가 "어느 예산에서요?"라는 답을 들음. 그날 저녁 남편에게 "행정실은 왜 저래"라고 투덜댔음
- 그 뒤 예산 과목, 금액, 근거 규정을 적은 메모를 들고 가자 실장이 "이렇게 주시면 제가 일하기 편합니다"라고 하며 바로 처리해 줌
- 지금은 "실장님이 된다고 하면 감사 때 문제없다"고 동료들에게 말함
- 실장이 IT 용어를 물어보면 학교 행정 비유로 답하려고 노력함. "서명 키는 교사 개인 도장이고, 실행기는 그 도장을 대조하는 행정실 금고예요"
- 실장이 "교육은 부장님 영역, 감사는 제 영역"이라고 선을 그을 때, 은하는 그 선이 오히려 편하다고 느낌

### 13.4 자주 하는 말

- "그거 구조 문제예요."
- "학생 입장에서 몇 분 걸려요?"
- "명세 몇 절에 있어요."
- "작게 해 보고 숫자로 말할게요."
- "회사 가면 매일 하는 일이에요."
- "평가에는 안 씁니다."

- 업체 개발자와 직접 소통할 창구가 없는 경우

## 15. 사용 시나리오

### 시나리오 1: 명세 검토 (2026. 10. 27.)

1. 데모 이틀 전 밤, 남편과 명세를 끝까지 읽음
2. 3.5에서 `POST /requests`가 내부망 전용인 걸 보고 "집에서 숙제 못 하겠네"라고 메모함
3. 2.2의 `SAME_DEPT_OTHER`가 부서 단위인 걸 보고 학생 간 승인 시범을 다시 생각함
4. 다음 날 질문 15개를 정리해 업체 개발자에게 메일로 보냄

### 시나리오 2: 시범 2주차 DB 작업 수업

1. 2학년 3반 한 팀이 "회원 테이블에 닉네임 열 추가" Plan을 만듦. DB, HIGH
2. 담당 우다현 교사가 승인 화면에서 `target`이 자기 팀 스키마인지 확인하고 서명
3. 학과부장 승인이 필요해서 은하에게 알림이 감. 은하는 다른 반 수업 중이라 12분 뒤 서명
4. 그동안 팀은 다음 과제를 함. 은하는 HIGH 작업의 학과부장 승인을 "담당 교사 2명"으로 바꿀 수 있는지 승인 기준표를 확인함

### 시나리오 3: 금지 규칙 시험

1. 진세호 교사가 10월 사고와 같은 프롬프트를 시범 계정으로 그대로 넣어 봄
2. Plan에 `DROP DATABASE`가 포함되어 `422 FORBIDDEN_TASK`로 제출이 막힘
3. 진 교사가 "이걸 그 학생한테 보여 주고 싶어요"라고 말함. 은하는 사고 당사자 학생 동의를 받고 수업 사례로 씀 (이름 비공개)

### 시나리오 4: "오늘밥" 배포와 킬 스위치

1. 동아리 3학년 부장이 급식 메뉴 화면 수정과 배포 Plan을 만듦 (CODE_FEATURE + DEPLOY)
2. 진세호 교사와 은하가 서명하고 배포 실행
3. 배포 중 알림 발송 대상이 전교생으로 잘못 잡힌 걸 로그 스트림에서 발견, 은하가 킬 스위치로 중단
4. `KILLED`, 남은 작업은 `SKIPPED`. 감사 로그에 은하 이름과 사유가 남은 걸 확인함

### 시나리오 5: 졸업과 기간제 계약 종료 (2027년 2월)

1. 3학년 동아리원 5명 졸업, 우다현 교사 계약 종료 (2027. 2. 28.)
2. 우 교사 서명 키를 폐기하고 담당 프로젝트를 다른 교사로 바꾸자, 우 교사 서명이 필요했던 승인 대기 요청이 `REAPPROVAL_REQUIRED`로 바뀜
3. 은하는 이 처리를 2월 마지막 주에 한꺼번에 할 수 있는 체크리스트를 만듦

## 17. 한 줄 요약

구은하는 **사고를 막는 일과 가르치는 일을 하나로 묶고 싶은** 개발자 출신 학과부장입니다. 학생에게는 관리자 권한도 서명 키도 주지 않으면서 교사 승인이 수업 시간 안에 끝난다는 것을 시범 숫자로 보여 주면, 학교 안에서 가장 앞장서 도입을 이끌고 다른 학과로 넓히는 사람이 됩니다.
