### 1.4 웹 서비스 운영 위치와 E2EE의 관계 정리

- 보완 설명 1의 (나) "승인 envelope을 웹 서비스가 열지 못한다"는 점은 letter-01 필수 조건 3(개인정보 최소화·위탁)과 묶어 판단함
- 단, **E2EE로 승인 envelope을 못 연다는 것과, 웹 서비스가 계정·프롬프트·Plan 본문·실행 로그를 저장하는지는 별개 문제**임을 재확인. 승인 서명 envelope만 보호된다고 학생 개인정보 전반이 보호되는 것이 아님
- 따라서 letter-01 6항 4번(계정·프롬프트·Plan·실행 로그별 수집 항목, 저장 위치, AI 외부 전송·재위탁, 보관 기간, 파기)과 5번(위탁 계약서안)은 그대로 유효하며, E2EE 설명으로 대체되지 않음
- 웹 서비스 자체의 운영 위치(외부 클라우드/교내 설치)와 보안 인증 요구(letter-01 6항 3번)도 그대로 유지. "실행기가 학교에 있다"가 "웹 서비스도 학교에 있다"를 뜻하지 않음

## 2. 논의 내용

### 2.1 실행기가 "서버 증설"인 줄 알았던 오해

- 노상규: 1차 때는 "실행기 서버를 새로 사야 하나, 약 450만 원 별도 과목"으로 메모해 뒀음. 업체 보완 설명을 받고 "무거운 러너가 아니라 경량 컴포넌트"라는 점을 구은하에게 확인하려 함
- 구은하: 실행기는 Plan 해시를 직접 만들고 서명·nonce를 검증하는 서명 검증기이고, 승인 envelope을 E2EE로 받아 실행기 공개키로만 푼 뒤 6단계 통과 시 웹쉘로 로컬 작업을 하는 컴포넌트라고 정리. 무거운 인프라가 아니라는 설명에 "운영 부담 평가를 낮출 수 있다"고 동의하되, 경량은 업체 주장이므로 1단계에서 사양·자원으로 확인하자고 함
- 탁민우(배석): 실습망 서버 자원이 한정적이라 경량이면 `hanbit-lab-04`에 기존 프로젝트와 분리해 올릴 수 있을지 1단계에서 보겠다고 함

### 2.2 단일 컴포넌트 장애 — 이중화냐 페일오버냐

- 노상규: 실행기가 하나뿐이면 그게 죽는 날 수업이 통째로 멈추는 것 아니냐고 다시 물음. 다만 학교가 이중 서버를 사 달라고 요구하는 건 예산상 무리라는 것도 인정
- 구은하: 이중화(HA)를 강하게 요구하는 상황은 아니라고 정리. 경량 컴포넌트이므로 재기동이 빠른지, 장애 시 요청 상태가 유지되는지(`502 EXECUTOR_UNAVAILABLE` 뒤 상태 불변), 복구·대체 수업 절차가 있는지의 "페일오버 관점"으로 보자고 함. 이중화 투자가 아니라 운영안의 복구 절차로 다룸(△ 수준)
- 노상규: 그 선이면 교장선생님께 "서버를 더 사자는 게 아니라, 멈췄을 때 어떻게 되돌리는지 적어 뒀다"고 설명할 수 있어 좋다고 함

### 2.3 Tailscale — 운영에도 계속 쓰는 건지

- 노상규: 1차 회의 때 "Tailscale로 학교 내부망에 접속"이라는 말이 나와서, 운영에도 외부 업체 네트워크를 상시로 끼는 거면 교육청 보안 지침에 걸린다고 걱정했음. 여동생(전주시청)이 "클라우드 쓰려면 보안 인증부터 보라"고 한 말이 걸렸다고 함
- 구은하: Tailscale은 업체의 개발·테스트 단계 임시 구성이고, 운영 배포는 교내 내부망(실습망) 연결이라고 업체가 보완 설명을 줬다고 전함. 운영에서 웹 서비스와 실행기 사이는 mTLS, 내부망 대역은 학교 관리자가 설정하며, 교내 실습망에 내부 설치형으로 둘 수 있다고 함
- 탁민우(배석): 실습망은 업무망·인터넷망과 분리돼 있어, mTLS 인증서와 대역·방화벽 관리 주체를 미리 정하면 내부 설치형이 맞다고 봄. 다만 운영에서 Tailscale을 "정말 안 쓰는지"는 구성도로 받아야 한다고 함
- 노상규: "개발은 Tailscale, 운영은 교내 mTLS"를 업체 공문과 그림으로 받고, 11. 18. 여태민 주무관 협의에서 운영 시 외부 네트워크 상시 사용 여부를 확인하기로 함

### 2.4 E2EE가 개인정보 문제를 다 푼 건 아님

- 노상규: "웹 서비스가 봉투를 못 연다"는 말을 듣고 "그럼 학생 정보도 업체가 못 보는 거냐"고 물음
