## 2. 실제 공개 개념으로 본 기술 판단 배경

> 아래 서비스·개념은 모두 AWS가 공개한 것입니다.

- **IAM/STS**: 최소 권한, 임시 자격 증명. "운영 자격을 사람·에이전트 노트북에 두지 않는다"는 원칙을 이미 구현하는 수단
- **CloudTrail / Config**: 모든 API 호출·구성 변경을 감사 기록. "누가 언제 무엇을" 문제의 기존 해법
- **KMS**: 키 관리·서명. BeforeAI의 "서명 E2EE"에 대응하는 당사 기본 블록
- **Step Functions / EventBridge**: 승인 게이트가 있는 워크플로. "사람이 승인해야 다음 단계"를 구성 가능
- **셀 기반 아키텍처·Nitro 격리**: 단일 실행기 구성(명세 5장)과 대비되는 당사의 가용성·격리 전제
- **Correction of Error (COE)**: 사고 후 근본 원인·재발 방지를 문서화하는 공개된 운영 문화. Daniel이 "사람 교육이 아니라 메커니즘으로 막는다"고 말하는 배경

### 3.3 Daniel이 제안한 자체 구축 스케치 (개념 참고)

> BeforeAI 설계를 당사 블록으로 옮긴 가상의 내부안.

1. AI 에이전트 변경을 **Step Functions 승인 게이트**가 있는 파이프라인으로만 운영에 반영
2. 변경 Plan의 정규화 해시를 **파이프라인 실행 측(데이터 플레인)에서 재계산**해 요청 측 값과 대조 (BeforeAI 2.3 개념)
3. 승인 서명은 **KMS 비대칭 키**로, 승인자별 키·권한은 IAM으로 분리 (2.4, 4.5 개념)
4. 리플레이 방지는 멱등성 토큰(=nonce) + DynamoDB 조건부 쓰기 (2.4 개념)
5. 전 과정 **CloudTrail/Config**에 기록, GuardDuty·EventBridge로 이상 탐지·경보
6. 운영 자격은 **IAM/STS 임시 자격**만, 에이전트·노트북에 장기 키 없음

- Daniel 메모: "BeforeAI가 제품으로 묶어 준 걸, 우리는 블록으로 흩어 가지고 있다. 통합은 우리 일."

### 3.4 Daniel이 벤더에게 남긴 말

- "설계 원칙은 정말 좋아요. 다만 우리한테 파는 건 번지수가 틀렸어요. 우리는 이걸 만드는 쪽이에요."
- "진짜 시장은 우리 위에서 도는 고객들이에요. 그들은 IAM이나 Step Functions를 이 수준으로 엮을 여력이 없거든요. BeforeAI가 그걸 제품으로 줘요."
- "데이터가 고객 계정·리전을 안 벗어난다는 걸 보장하면(예: 고객 VPC 내 배포, PrivateLink), 우리 고객들한테 훨씬 잘 팔릴 거예요."
