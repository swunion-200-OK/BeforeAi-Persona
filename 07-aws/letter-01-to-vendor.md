# AWS — 벤더 평가 회신

> **실제 공개 정보 + 설계용 가정 혼합 문서입니다.**
> - 실제(공개): AWS의 공개 개념·서비스(IAM, CloudTrail, KMS, Step Functions, PrivateLink 등), "security is job zero", 자체 구축 경향 등 널리 알려진 특성.
> - 가정(설계): 발신 담당자·연락처·문서번호·사건·결론은 전부 가상. 실존 인물 실명·비공개 내부 정보는 쓰지 않았습니다.
> 내용은 `persona-vendor-risk.md`, `persona-principal-engineer.md`, `meeting-01-adoption-review.md`를 따릅니다. 결론은 **외부 도입 부적합(정중한 거절) + 설계 개념은 참고**입니다.

1. 데모와 자료 제공에 감사드립니다. 당사 조달·보안 양 관점에서 검토한 결과를 아래와 같이 회신합니다.

2. 결론을 먼저 전합니다. 당사는 **BeforeAI를 외부 제품으로 도입하지 않기로** 결정하였습니다. 이는 제품의 설계 품질 문제가 아니라, **당사의 운영 원칙상 이런 통제를 외부에서 도입하기보다 내부 역량으로 구축하기 때문**입니다.

3. 당사의 설계 평가 (긍정)

   당사는 아래 설계 원칙을 높게 평가합니다.

   | 번호 | 설계 | 명세 근거 | 평가 |
   | --- | --- | --- | --- |
   | 1 | 컨트롤 플레인 불신·데이터 플레인 재검증 (실행기가 Plan 해시를 직접 생성) | 2.3, 5장 | 통제 구조로 올바른 방향 |
   | 2 | 승인 서명 기기 생성·실행기 공개키 복호화 | 2.4, 4.5 | 중간 위조 불가. 견고함 |
   | 3 | nonce 1회 소진, 검증 6단계 fail-closed | 2.4, 5.1 | 리플레이 방지와 안전한 실패 |

4. 외부 도입을 하지 않는 사유

   | 번호 | 사유 | 설명 |
   | --- | --- | --- |
   | 1 | 운영 경로의 새 공격 표면 | 외부 실행기·웹 서비스를 운영 변경 경로에 두는 것은 당사 보안 기준상 보수적으로 판단 |
   | 2 | 데이터 경계·레지던시 | AI 분석 단계의 데이터 흐름(명세 4.1)이 당사 계정·리전·서브프로세서 경계 안에 머무는지 확인 불가 |
   | 3 | 자체 역량과 중복 | 해시 재검증, 서명(KMS), 승인 게이트(Step Functions), 감사(CloudTrail/Config), 자격 격리(IAM/STS)를 당사 기존 역량으로 구성 가능 |
   | 4 | 가용성·아키텍처 | 단일 실행기 구성(명세 5장)은 당사 가용성·격리 전제와 불일치 |
   | 5 | 출구 전략 | 운영 통제의 외부 벤더 종속(lock-in)을 지양 |

5. 피드백 (제품 방향)

   당사는 경쟁 관점이 아니라, 설계를 좋게 본 입장에서 아래를 전합니다.

   - 당사와 같은 대형 클라우드 사업자는 이 통제의 **구매자가 아니라 구축자**입니다. 그러나 **당사 플랫폼 위에서 운영하는 다수의 기업 고객**은 IAM·Step Functions·KMS를 이 수준으로 직접 엮을 여력이 없는 경우가 많습니다. 그들이 BeforeAI의 적합한 시장이라고 봅니다.
   - **데이터가 고객의 계정·리전 경계를 벗어나지 않는 배포 모델**(예: 고객 VPC 내 배포, PrivateLink 연결, 분석의 고객 경계 내 수행)을 명확히 제시하면, 그 고객들에게 설득력이 크게 올라갈 것입니다.
   - AI 분석 단계의 데이터 흐름·서브프로세서·리전을 명세에 명시하는 것을 권합니다. 이는 당사뿐 아니라 규제 산업 고객 대부분의 1차 질문입니다.

6. 거듭 감사드립니다. 이번 결정은 제품의 우수성과 무관하며, 당사의 구축 지향 운영 원칙에 따른 것입니다. 귀사의 발전을 기원합니다.

끝.
