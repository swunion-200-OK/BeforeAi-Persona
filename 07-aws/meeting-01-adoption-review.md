## 1. 결정 사항

### 1.1 결론: 외부 제품 도입 부적합, 자체 구축 검토

- BeforeAI를 **외부 제품으로 도입하지 않음.** 운영 통제 경로에 외부 벤더를 넣는 것은 당사 기준상 one-way door에 가까움
- 다만 **설계 개념(컨트롤 플레인 불신·데이터 플레인 재검증, 서명 E2EE, nonce, fail-closed)은 높게 평가**하고, 내부 통제 설계에 참고
- 동일 문제를 **working backwards로 내부 정의하고, 기존 당사 서비스(IAM/STS, CloudTrail, KMS, Step Functions, Config)로 자체 구축**하는 안을 별도 트랙으로 검토
- 벤더에는 **정중한 회신**: 설계는 높이 평가하나 당사는 이런 통제를 내부 구축하는 조직이며, 진짜 적합 시장은 당사 위에서 도는 고객들이라는 피드백 포함

### 1.2 외부 도입 부적합 사유

| 번호 | 사유 | 근거 |
| --- | --- | --- |
| 1 | 운영 경로에 새 공격 표면 | 외부 실행기·웹 서비스가 운영 변경 경로에 유입. "security is job zero" 기준 보수적 |
| 2 | 데이터 경계·레지던시 불명 | AI 분석 데이터 흐름(명세 4.1)이 당사 계정·리전·서브프로세서 경계 안인지 확인 불가 |
| 3 | 자체 역량과 중복 | 해시 재검증·서명·승인 게이트·감사·자격 격리가 IAM/KMS/Step Functions/CloudTrail로 이미 가능 |
| 4 | 단일 실행기 가용성 | 명세 5장 단일 실행기는 당사 셀 기반·다중화 전제와 불일치 |
| 5 | 출구 전략·lock-in | 벤더 종료·전환 시 운영 통제가 벤더에 묶임 |

### 1.3 자체 구축 스케치 (개념 참고)

- 변경 반영은 Step Functions 승인 게이트 파이프라인으로만
- Plan 정규화 해시를 실행 측(데이터 플레인)에서 재계산·대조 (BeforeAI 2.3 개념)
- 승인 서명은 KMS 비대칭 키, 승인자 권한은 IAM 분리 (2.4, 4.5 개념)
- 리플레이 방지는 멱등성 토큰 + 조건부 쓰기 (2.4 개념)
- 전 과정 CloudTrail/Config 기록, GuardDuty·EventBridge 경보
- 운영 자격은 IAM/STS 임시 자격만, 에이전트·노트북에 장기 키 없음

### 1.4 벤더 피드백 요지

- 설계 원칙은 우수. 다만 당사는 구매자가 아니라 구축자
- 데이터가 고객 계정·리전을 벗어나지 않는 배포 모델(고객 VPC 내, PrivateLink 등)을 제시하면, 당사 고객(기업)에게 설득력이 커짐

## 2. 논의 내용

### 2.1 설계 평가

- Daniel: 해시 재검증·서명·nonce·fail-closed는 당사 내부 통제와 같은 결. 설계 자체는 정확하다고 평가
- Grace: 설계 품질과 도입 적합성은 별개. 외부 벤더를 운영 경로에 넣는 리스크가 먼저라고 선을 그음

### 2.2 빌드 vs 바이

- Daniel: 핵심 블록이 전부 당사에 있음(IAM/KMS/Step Functions/CloudTrail). BeforeAI가 제품으로 묶은 걸 당사는 블록으로 흩어 보유. 통합은 당사 일
- Grace: 자체 구축 비용과 외부 도입 TCO를 나란히 놓으면, 운영 통제 같은 핵심은 빌드가 합리적. one-way door라 더 그렇다고 정리

### 2.3 데이터 경계

- Grace: AI 분석 단계 데이터 흐름이 명세에 없음(4.1). 소스코드·프롬프트가 경계를 벗어나는지, 서브프로세서가 누구인지 확인 불가
- Daniel: 이게 해결돼도 당사는 빌드 쪽이지만, 당사 고객들에게는 이 명확성이 결정적일 것이라고 보탬

### 2.4 벤더에게 어떻게 말할지

- Grace: 제품을 깎아내리지 말고, "조달·리스크 관점의 결론"과 "설계는 우수"를 분리해 전하자
- Daniel: 기술 피드백으로 "진짜 시장은 당사 위 고객들", "데이터 경계를 보장하면 그들에게 잘 팔린다"를 더하자
- 결론: 1.4대로
