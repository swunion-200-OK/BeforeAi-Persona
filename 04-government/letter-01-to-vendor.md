1. 관련
   - 가. 귀사 서비스 소개 면담 (2026. 10. 13.(화), 우리 시 스마트도시정보과)
   - 나. 귀사 서비스 시연 (2026. 10. 28.(수), 우리 시 스마트도시정보과)
   - 다. 귀사 제공 「API 명세서(기능 명세서 결정 사항 반영본)」
   - 라. 우리 시 도입 방향 검토 회의 (2026. 11. 4.(수))

2. 우리 시는 외주 유지보수 인력이 AI 도구로 만든 변경을 공무원이 승인한 경우에만 운영 시스템에 반영하는 통제 수단을 검토하고 있습니다. 위 관련 검토 결과를 다음과 같이 알려 드리니, 아래 5항의 자료를 기한 내에 제출하여 주시기 바랍니다.

3. 검토 결론: **보류**
   - 가. 귀사 서비스의 승인·서명 검증 구조는 우리 시가 막고자 하는 사고 유형에 적합하다고 평가하였으나, 현재 명세로는 행정망 설치 요건, 암호모듈·인증 요건, 승인권자·감사 기록 요건을 충족하지 못하여 도입을 보류합니다.
   - 나. 이번 보류는 거부가 아니며, 2026년에는 구매를 약속하지 않습니다.
   - 다. 재검토 일정
     - 1) 2027. 1. 15.(금): 인증 신청 접수 증빙, 검증필 암호모듈 적용 버전, 귀사 사무실 시험 결과를 확인하여 우리 시 예산 요구 여부를 판단합니다. 접수 증빙이 없으면 예산 요구를 유보합니다.
     - 2) 2027. 6. 30.(수): 최종 재검토일로, 인증 진행 상황과 필수 기능 보완 실적을 확인하여 검토 계속 여부를 결정합니다.
     - 3) 계약과 운영 도입은 필요한 인증·검증과 우리 시 보안성 검토를 충족한 뒤에만 진행합니다. 보완 계획서 제출만으로 보류를 해제하지 않습니다.
   - 라. 우리 시는 같은 요구 기준을 검토 대상 다른 업체에도 같은 날 같은 기한으로 송부하였습니다. 이 공문과 귀사 회신 자료는 향후 발주에서 특정 업체를 우대하는 근거가 되지 않습니다.

4. 검토 결과

   **가. 검토를 계속하는 사유 (귀사 서비스의 강점)**

   | 번호 | 기능 | 명세 근거 | 우리 시 평가 |
   | --- | --- | --- | --- |
   | 1 | 실행기가 Plan 해시를 RFC 8785 정규화와 SHA-256으로 직접 만들고 웹 서비스가 보낸 해시를 쓰지 않음 | 2.3 | 반입한 변경과 승인한 변경이 같은지 기계로 확인하지 못한 우리 시 사고 원인에 맞는 구조임 |
   | 2 | 승인 서명을 승인자 기기에서 만들고 실행기 공개키로 암호화하며, 웹 서비스는 암호문만 전달 | 2.4, 4.5 | 웹 서비스 관리 권한을 가진 사람도 서명을 바꿀 수 없음 |
   | 3 | 서명마다 1회용 nonce, 재사용 시 `NONCE_ALREADY_USED` | 2.4, 5.1 | 승인 한 번으로 두 번 반영되는 일을 막음 |
   | 4 | 실행기 검증 6단계 중 하나라도 실패하면 실행하지 않고 `VERIFICATION_FAILED`와 경보 | 5.1 | 실패 시 닫힌 쪽으로 동작함 |
   | 5 | 금지 규칙 해제는 실행기 로컬 콘솔에서 관리자가 다시 확인해야 반영 (`RELEASE_PENDING`) | 3.4, 5장 | 원격에서 통제를 풀 수 없음 |
   | 6 | 웹 코드 에디터 변경도 승인·서명 절차를 거치고, 기준 커밋이 바뀌면 `409 EDIT_CONFLICT` | 3.8, 4.7 | 에디터를 이용한 우회 경로가 없음 |
   | 7 | 프로젝트 담당자 2명 이상 (`409 OWNER_MINIMUM`), 빠진 담당의 승인 대기 건은 `REAPPROVAL_REQUIRED` | 3.3 | 1인 담당 구조를 바꿀 근거가 됨 |
   | 8 | 공개키 등록에 관리자 서명이 필요하고, 폐기는 실행기에 바로 반영 | 3.2 | 외주 계약 종료 시 키를 바로 무효로 할 수 있음 |
   | 9 | 킬 스위치와 전사 일괄 중단이 서명 없이 즉시 동작 | 4.6, 3.2 | 반영 중 이상 발생 시 바로 멈출 수 있음 |
   | 10 | 실행기 연결 실패 시 `502 EXECUTOR_UNAVAILABLE`, 요청 상태 유지 | 4.3 | 연결 문제를 이유로 승인 절차를 건너뛰지 않음 |
   | 11 | 상태를 바꾸는 모든 API에 접속 환경·IP를 포함한 감사 로그 자동 기록 | 1.1, 4.8 | 감사 대응의 기본 자료가 됨 |

   **나. 보류 사유**

   | 번호 | 사유 | 명세 근거 | 현재 상태 |
   | --- | --- | --- | --- |
   | 1 | 행정망 내부 설치와 통신 흐름 | 1.1, 4.1 | 실행기 구간이 Tailscale을 전제로 하나, 우리 시 행정망은 인터넷과 분리되어 있어 외부 조정 서버가 필요한 구성을 쓸 수 없음. 설치·라이선스 인증·알림의 외부 통신 여부와 AI 분석 위치가 명세에 없음 |
   | 2 | 암호모듈과 제품 인증 | 2.4, 5장 | 서명 Ed25519, 암호화 HPKE(X25519 + AES-256-GCM), mTLS에 쓰는 암호모듈이 검증필 암호모듈(KCMVP) 요건을 충족하는지 확인되지 않음. 보안적합성 검증에 필요한 제품 인증(CC인증 또는 보안기능 확인서 등)의 보유·적용 근거가 없음 |
   | 3 | 승인권자·외부망·감사 기록 | 1.3, 2.2, 3.6, 3.9, 4.8 | 역할이 `ADMIN`·`DEPT_MANAGER`·`EMPLOYEE`뿐이라 공무원과 외주 인력을 구분해 승인권자를 공무원으로 한정할 수 없음. 외부망에서 코드 수정 승인이 허용됨. 감사 로그 보관 기간 설정, 파일 내보내기, 위변조 방지가 없음 |

   - 서비스가 인터넷 SaaS로만 제공되는 경우, 클라우드 보안인증(CSAP) 보유 여부와 관계없이 이번 검토의 "행정망 내부 설치·외부 전송 없는 구성" 필수 요건 미충족으로 기록합니다.

   **다. 우려 사항 (필수 조건 외 확인 필요)**

   | 번호 | 내용 | 명세 근거 | 우리 시 우려 |
   | --- | --- | --- | --- |
   | 1 | 로그인이 사번·비밀번호와 OTP | 3.1 | 우리 시 내부 시스템은 행정전자서명(GPKI) 인증서나 통합인증 연동이 기본임. 로그인 인증과 작업 승인 서명을 구분해 검토 필요 |
   | 2 | 승인자 개인키를 기기에 보관 | 2.4, 3.1 `/me/signing-keys` | 업무 PC 교체·재설치·분실 시 키 보호와 회수 방법 |
   | 3 | 계정 비활성화 시 기존 세션 처리 | 3.2 `PATCH /admin/users/{userId}`, 1.1 리프레시 토큰 | 비활성화 즉시 기존 로그인 세션과 리프레시 토큰이 끊기는지 명세에 없음 |
   | 4 | Plan 원문과 실행 로그의 개인정보 | 2.2 `content.query`, 3.5 `/requests/{requestId}/logs/stream` | 민원 데이터 조회 결과가 Plan·로그에 남으면 그 자체가 개인정보 파일이 됨. 마스킹과 보관 기준 필요 |
   | 5 | 실행기 단일 구성 | 5장 | 이중화 시 nonce 소진, 키 폐기, 정책이 두 실행기에 같게 반영되는지 |
   | 6 | 알림이 Slack 전용 | 3.1, 3.2 | 행정망에서 Slack을 쓸 수 없음 |
   | 7 | 승인 서명에 만료 없음 | 2.4 | 승인 후 오랜 기간이 지나 실행되는 경우의 처리 |
   | 8 | 실행기의 Plan 전용 웹쉘 세션 | 5.1 | 운영 서버에서 실행 가능한 명령 범위 제한과 세션 기록 |
   | 9 | 접속 환경 판별 대역 | 1.1 `X-Network` | Tailscale 대역(100.64.0.0/10)이 기본 내부망으로 간주됨. 우리 시는 행정망 대역만 내부로 보아야 함 |

5. 요청 사항

   **가. 필수 요청 (보류 해제의 전제)**

   | 번호 | 요청 기능 | 요청 내용 (예시 형태이며, 귀사 설계에 맞는 동등한 방식도 검토함) |
   | --- | --- | --- |
   | 1 | 행정망 내부 설치형 | 웹 서비스와 실행기를 모두 우리 시 서버에 설치하고, 인터넷 연결이 없는 상태에서 설치·라이선스·운영이 가능할 것. 실행기 주소(`https://executor.{tailnet}/v1`)를 행정망 내부 주소로 설정할 수 있고, Tailscale 없이 웹 서비스 ↔ 실행기 mTLS로 동작할 것. 접속 환경 판별 대역을 관리자가 설정할 수 있을 것 (예: `PUT /admin/policy`의 `internalCidrs`) |
   | 2 | 검증필 암호모듈 | 승인 서명(2.4), envelope 암호화(4.5 `envelope.alg`), mTLS(5장)에 검증필 암호모듈과 그 모듈의 검증대상 알고리즘을 쓸 수 있을 것. 모듈 제품명·버전·검증 범위를 제출할 것 |
   | 3 | 공무원 승인권자 한정 | 계정에 소속 구분 추가 (예: `POST /admin/users`, `PATCH /admin/users/{userId}`의 `affiliation: PUBLIC_OFFICIAL` 또는 `CONTRACTOR`, `contractId`). 승인 기준표(`PUT /admin/approval-matrix`)에서 승인권자를 공무원으로 한정하는 조건을 둘 것. `CONTRACTOR` 계정의 `POST /me/signing-keys`와 `POST /admin/signing-keys/{keyId}/register`는 거부할 것. 실행기 로컬 정책 검증(5.1 3·5단계)에서도 같은 조건을 확인하고 실패 원인을 남길 것 (예: `failedChecks`의 `APPROVER_NOT_ELIGIBLE`) |
   | 4 | 외부망 기능 전면 차단 | 정책으로 외부망 접속과 외부망 승인을 모두 끌 수 있을 것 (예: `PUT /admin/policy`의 `externalAccess: DISABLED` 설정 시 외부망 호출 전부 `403 INTERNAL_NETWORK_ONLY`) |
   | 5 | 감사 로그 보관·내보내기·위변조 방지 | 생성일부터 2년 이상 보관 기간 설정(예: `auditRetentionDays: 730` 이상), `GET /audit-logs` 검색 조건을 그대로 적용한 파일 내보내기(예: `GET /audit-logs/export?format=CSV`), 기록의 위변조 여부를 확인하는 방법 (예: 해시 연결과 `GET /audit-logs/integrity`) |
   | 6 | 계약 종료 시 차단과 결과 제출 | 계정 비활성화 시 기존 세션·리프레시 토큰 즉시 무효화. 대상자, 처리 시각, 성공·실패, 재처리 결과를 파일로 제출할 수 있을 것 |
   | 7 | AI 분석 위치와 외부 전송 없는 구성 | AI 분석 위치를 공개하고, 외부 전송 없이 분석하거나 분석을 끄고 외부에서 반입한 패치를 Plan으로 등록할 수 있을 것 (예: `PUT /admin/policy`의 `aiAnalysis: DISABLED`, 반입 패치 등록 시 `source: IMPORTED_PATCH`와 반입 파일 해시 기록) |
   | 8 | 승인자 본인 확인과 개인키 보호·회수 | 승인자 본인 확인 방식, 개인키를 내보낼 수 없게 보관하는 방식, 분실·교체 시 폐기와 재등록 절차 |

   - 위 필수 요청의 기준은 붙임 1 요구 기준표로 다른 업체에도 같이 요청하였습니다. API 예시는 귀사 명세에 맞춘 것입니다.
   - 감사 로그 2년은 「개인정보의 안전성 확보조치 기준」 제8조 제1항의 접속기록 보관 기간을 참고한 우리 시 요구 기준입니다. 우리 시 내부 규정에 더 긴 기간이 있으면 별도로 알려 드립니다.

   **나. 희망 요청**

   | 번호 | 요청 기능 | 요청 내용 |
   | --- | --- | --- |
   | 1 | 사업자·계약 단위 일괄 처리 | 계약 단위로 계정 비활성화와 키 폐기를 한 번에 처리 (예: `POST /admin/contracts/{contractId}/terminate`)하고 결과 보고서 조회 |
   | 2 | 계정 예약 만료 | 계정 생성 시 계약 종료일을 넣어 자동 비활성화 (예: `expiresAt`) |
   | 3 | 행정전자서명(GPKI) 서명 | 승인 서명을 GPKI 인증서 또는 보안토큰으로 할 수 있을 것. 어려우면 동등한 대안과 근거 제시 |

   - 희망 요청이라도 계약 종료 통제를 대체할 방법이 없으면 도입 전에 해결이 필요합니다.

   **다. 장기 검토 요청 (로드맵 회신)**

   - 실행기 이중화 구성 (nonce 소진, 키 폐기, 정책 동기화 방식 포함)
   - 우리 시 통합 로그 관리 연계 (예: syslog 전송, 실행기 검증 실패 경보 포함)
   - Slack 대신 내부 메신저·메일 알림
   - 기관 정책으로 승인 서명 유효 기간 설정
   - Plan 원문과 실행 로그의 개인정보 마스킹 규칙 설정

   **라. 시험 참여**
