# 페르소나: 노재석 (스마트도시정보과 정보보안팀장)

> "외주가 AI를 쓰는 건 이제 못 막습니다. 막을 건 하나예요. 공무원이 내용을 보고 승인하지 않은 변경은 운영에 한 줄도 안 들어가게 하는 것. 그런데 그 장치 자체가 우리 보안 기준을 못 넘으면, 그건 장치가 아니라 구멍입니다."

이 문서는 본 서비스(AI 작업 승인·서명·실행 통제 서비스) 도입 검토를 처음 제기한 정보보안 담당 팀장의 페르소나입니다.
기관(한빛광역시청), 부서, 가족, 주변 인물은 모두 설계용 가정입니다. 실제 기관·인물과 관계없습니다.
같은 부서 계약·예산 담당 주무관 페르소나는 `persona-contract-officer.md`에 있습니다.

## 2. MBTI와 성향

### 2.1 ISTP 특징이 드러나는 모습

- **내향(I)**: 회의에서 말을 길게 하지 않음. 결론만 한두 문장 말하고, 질문이 오면 그때 근거를 꺼냄
- **감각(S)**: 문서보다 직접 해 본 것을 믿음. 업체 시연을 보면 "제 노트북에서 한 번 더 해 보죠"라고 함
- **사고(T)**: 사고 보고서에 사람 이름보다 경로와 시각을 먼저 씀. "누가"보다 "어디로 들어왔나"
- **인식(P)**: 장애 대응은 빠르지만 행정 서류는 미루는 편. 배선영 주무관에게 기한을 여러 번 상기당함

### 2.2 MBTI를 대하는 태도

- 팀 회식 때 막내 석기원 주무관이 검사를 권해서 해 봄. "고치는 사람"이라는 설명이 마음에 들었다고 함
- 배선영 주무관이 ESTJ라는 걸 듣고 "그래서 기한을 그렇게 챙기는구나"라고 납득함
- MBTI를 업무에 쓰는 건 반대. "보안 사고는 성격 안 가리고 납니다"

### 2.3 성격 요약

| 강점 | 약점 |
| --- | --- |
| 실물 감각. 서버실 랙 배치와 방화벽 정책 번호를 외움 | 말이 짧아 비전산직 직원은 무슨 뜻인지 다시 물어야 함 |

| 원칙이 분명함. "망 넘어가는 건 안 된다"에는 예외를 두지 않음 | 새로운 기술에 호기심이 많아 업체 시연에 쉽게 끌림 |

| 후배를 잘 가르침. 팀원 9명 중 4명이 정보보안기사를 땀 | 혼자 밤새 해결하고 보고를 늦게 해서 과장에게 지적받음 |

### 2.4 스트레스 반응

- 큰일이 생기면 말이 더 짧아지고 메신저 답이 "네", "확인" 두 단어가 됨
- 사고 처리가 끝나면 서버실 바닥에 앉아 한참 아무 말 없이 있음. 팀원들은 그때 말을 걸지 않음
- 스트레스가 쌓이면 주말에 아파트 지하 주차장에서 차를 직접 손세차하거나, 오래된 라디오를 분해해서 고침

### 2.5 의사결정 스타일

1. 경로를 그린다 ("데이터가 어디서 어디로 가는지" 종이에 화살표로)
2. 망 경계를 확인한다 (행정망, 인터넷망, 외부 중 어디를 건너는지)
3. 기준에 맞는지 본다 (국가 정보보안 기본지침, 시 정보보안 업무 규정, 인증 요건)
4. 직접 시험한다 (가능하면 시험 환경에서 일부러 깨 봄)
5. 기준에 안 맞으면 기술이 아무리 좋아도 "보류"라고 씀. 단 대안을 같이 씀

### 3.2 아내 구혜란

- 병원 전산 시스템의 "투약 이중 확인" 절차를 매일 씀. 재석이 본 서비스 구조를 설명하자 "우리는 위험한 약은 간호사 두 명이 확인하고 서명해. 그거랑 같네"라고 바로 이해함
- 이 비유를 재석이 과장 보고 때 그대로 씀. "고위험 작업은 담당자 두 명 중 한 명 서명, 마약류처럼 금지 작업은 아예 처방이 안 나감"
- 재석이 밤에 비상 호출을 받고 나가면 "차 조심"이라고만 말함. 25년째 같음
- 병원이 2024년 전자의무기록을 바꿀 때 개인정보 영향평가를 받는 과정을 옆에서 봐서, 재석보다 영향평가 일정을 더 현실적으로 말함

### 3.3 아들 노승원

- 재석이 본 서비스 API 명세를 집에서 보여 주자, 2.4절을 읽고 "아빠, Ed25519랑 X25519는 국내 검증 목록에 없을걸?"이라고 먼저 말함
- 재석은 "그건 아빠도 안다"고 했지만, 실제로 검증대상 알고리즘 목록을 다시 찾아본 건 그날 밤
- 승원이 "Tailscale은 조정 서버가 밖에 있잖아. 망분리면 안 될 텐데"라고 말한 것도 메모해 둠
- 재석은 승원이 공무원보다 보안 회사를 가길 바라는데, 승원은 "아빠처럼 공공 쪽도 괜찮아 보여"라고 해서 기분이 복잡함

- 수능이 2주 남아 집안이 조용함. 재석은 11. 19.(목) 연가를 미리 냄

- 대학 전자계산학과에서 네트워크 수업을 가장 좋아함. 졸업 작품은 학과 서버의 접속 기록 분석 프로그램

### 4.3 기억에 남는 성공과 실패

**성공: 2011~2013년 망분리 구축**
- 직원 PC 약 3,800대를 행정망·인터넷망으로 나누는 사업 실무를 맡음
- 직원 반발이 컸지만 망간 자료전송시스템 승인 절차를 간소화해 불만을 줄임 (승인 대기 평균 20분 → 5분)
- 이 일로 "망 경계는 노재석에게 물어봐라"는 평판을 얻음

**실패: 2018년 홈페이지 첨부파일 노출**
- 시 홈페이지 게시판 개편 때 외주 개발자가 첨부파일 접근 권한 검사를 빠뜨림
- 민원 첨부파일 약 340건이 검색엔진에 노출됐고, 개인정보 유출 신고와 정보주체 통지를 함
- 재석은 보안성 검토 담당이었고 "변경 검토 범위에 게시판 첨부 기능이 빠졌다"는 사실을 뒤늦게 알게 됨
- 이후 "외주 변경은 사람이 내용을 보고, 그 기록이 남아야 한다"는 원칙을 세움

**위기: 2026. 9. 10.(목) 민원 시스템 사고 위기**

## 10. 본 서비스 도입 검토

### 10.1 재석이 정의한 문제

- 외주 인력이 만든 변경(AI 도구로 만든 것 포함)은 공무원이 내용을 보고 승인한 것만 운영 시스템에 반영되어야 한다
- 승인 내용과 실제 반영 내용이 같다는 것을 기계가 검증해야 한다. 사람 눈으로 매일 두 시간 보는 방식은 오래 못 간다
- 그 통제 장치 자체가 시의 보안 기준(망분리, 인증, 암호모듈, 개인정보 보호)을 넘어야 한다

### 10.2 선택지 비교 (재석이 과장에게 보고한 표)

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 본 서비스 도입 | 실행기가 해시를 직접 만들고 서명을 검증하는 구조. 웹 서비스가 뚫려도 실행 안 됨 | 암호 알고리즘, Tailscale, AI 분석 위치, 인증 여부가 시 기준과 맞지 않음 |
| 기존 절차 강화 (검증계 의무 시험, 망간 자료전송 2인 승인, 변경 대장) | 바로 시행 가능. 비용 거의 없음 | 사람이 내용을 다 봐야 함. 반입한 파일과 운영에 반영된 파일이 같은지 기계적으로 확인 못 함 |
| 차기 통합유지보수 과업에 통제 체계 포함 | 계약상 의무로 만들 수 있음 | 사업자가 고른 도구를 사업자가 운영하면 감시받는 쪽이 감시 장치를 쥠 |

### 10.3 재석이 명세를 읽고 좋게 본 점

| 번호 | 기능 | 명세 근거 | 재석의 평가 |
| --- | --- | --- | --- |
| 1 | 실행기가 Plan 해시를 RFC 8785 정규화 + SHA-256으로 직접 만들고, 웹 서비스가 보낸 해시는 쓰지 않음 | 2.3 | "9월 사고는 반입 파일과 승인 파일이 같은지 아무도 기계로 확인 안 한 게 문제였다. 이건 그걸 막는다" |
| 2 | 승인 서명을 승인자 기기에서 만들고 실행기 공개키로 암호화. 웹 서비스는 envelope만 전달 | 2.4, 4.5 | "중간 서버를 믿지 않는 구조. 외주가 웹 서비스 관리자여도 서명을 못 바꾼다" |
| 3 | nonce 1회 소진, 재사용 시 `NONCE_ALREADY_USED` | 2.4, 5.1 | "승인 한 번으로 두 번 반영하는 일이 없다" |
| 4 | 실행기 검증 6단계 중 하나라도 실패하면 웹쉘을 열지 않음 | 5.1 | "실패하면 닫힌 쪽으로 간다. 보안 장치는 그래야 한다" |
| 5 | 검증 실패 시 `VERIFICATION_FAILED`로 바꾸고 관리자에게 경보 | 5.1 | "경보를 우리 통합 로그 관리로도 받을 수 있으면 좋겠다" |
| 6 | 금지 규칙 해제는 실행기 로컬 콘솔에서 관리자가 다시 확인해야 실제 반영 (`RELEASE_PENDING`) | 3.4, 5장 | "원격에서 통제를 풀 수 없다. 서버실 안에서만 풀린다" |
| 7 | 웹 코드 에디터도 승인·서명을 거치고, 기준 커밋이 바뀌면 `409 EDIT_CONFLICT` | 3.8, 4.7 | "에디터로 몰래 고치는 우회로가 없다" |
| 8 | 프로젝트 담당자 2명 이상 (`409 OWNER_MINIMUM`), 빠진 담당의 승인 대기 건은 `REAPPROVAL_REQUIRED` | 3.3 | "민원 시스템 담당이 탁지훈 혼자인 지금 구조를 바꿀 근거가 된다" |
| 9 | 상태를 바꾸는 모든 API에 접속 환경·IP를 포함한 감사 로그 자동 기록 | 1.1, 4.8 | "누가 언제 어디서 승인했는지 남는다" |
| 10 | 공개키 등록은 관리자 서명 필요, 폐기는 실행기에 바로 반영 | 3.2 | "외주 계약이 끝나는 날 키를 바로 죽일 수 있다" |
| 11 | 킬 스위치는 서명 없이 바로, 전사 일괄 중단 (`/admin/kill-all`) | 4.6, 3.2 | "반영 중 이상하면 바로 멈출 수 있다" |
| 12 | 실행기 연결 실패 시 `502 EXECUTOR_UNAVAILABLE`, 요청 상태 그대로 | 4.3 | "연결이 끊겼다고 절차를 건너뛰지 않는다" |

| 실행기 | Tailscale 내부망, mTLS | 행정망 내부 서버실. 웹 서비스와 같은 구간에서 mTLS (검증필 모듈) |

| 감사 로그 | 검색 API | 통합 로그 관리로 syslog 전송 + 파일 내보내기 + 보관 기간 설정 |

### 10.6 재석이 원하는 기술 검증(시험) 항목

| 시험 | 확인할 것 | 명세 근거 |
| --- | --- | --- |
| Plan 변조 | 웹 서비스 DB에서 Plan을 바꾼 뒤 실행 요청 → `VERIFICATION_FAILED`, `PLAN_HASH_MISMATCH` | 5.1 |
| 서명 재사용 | 같은 envelope 재전송 → `NONCE_ALREADY_USED` | 5.1 |
| 폐기 키 | 키 폐기 후 그 키로 만든 서명 제출 → `KEY_NOT_REGISTERED` | 3.2, 5.1 |

- 시험은 행정망과 연결되지 않은 별도 시험 환경에서 합성 데이터로만. 이건 배선영 주무관이 아니어도 재석 본인이 먼저 정한 원칙

## 11. 고민과 불안

- **좋은 구조, 맞지 않는 부품**: 구조는 9월 사고에 딱 맞는데, 암호 알고리즘·Tailscale·인증 때문에 지금 명세로는 보안성 검토 통과가 어려움. 본인이 검토자라 더 괴로움
- **금지 조치의 한계**: AI 도구 임시 금지가 길어지면 외주 인력이 몰래 쓸 것. 실제로 10월에 외주 PC 한 대에서 개인 계정으로 AI 서비스에 접속한 기록이 발견됨
- **탁지훈 주무관의 부담**: 외주 패치를 사람이 매일 두 시간 검토하는 지금 방식은 탁지훈이 휴가 가면 무너짐
- **자기 검토의 이해충돌**: 본인이 추진한 제품을 본인이 보안성 검토하는 모양이 될 수 있음. 그래서 검토는 팀원 석기원과 외부 자문을 함께 넣으려 함
- **업체 존속**: 업력이 짧은 업체가 인증에 1년을 쓸 여력이 있을지
- **보고 언어**: 과장과 배 주무관에게 HPKE, KCMVP를 한 문장으로 설명해야 함

## 12. 동기와 기대

- 9월 같은 일이 다시 생기지 않는 구조를 만드는 것. "운 좋게 막았다"를 "구조로 막았다"로 바꾸는 것
- AI 도구 금지를 근거 있게 풀어 주는 것. 외주 인력도 시 직원도 덜 고생하는 쪽
- 민원 시스템 담당을 2명 이상으로 늘리는 근거를 만드는 것
- 2018년 첨부파일 노출 이후 세운 "외주 변경은 기록이 남아야 한다"는 원칙을 시스템으로 남기는 것

## 13. 커뮤니케이션 방식

### 13.1 업체를 대할 때

- 시연 첫 10분 안에 "설치 패키지가 인터넷 없이 깔립니까?"를 물음
- 엔지니어와 직접 이야기하길 원함. 영업 담당이 답을 못 하면 "기술 담당 연락처 주세요"
- "인증 준비 중입니다"라는 답에는 "어느 기관에, 언제 신청했고, 접수 번호가 있습니까?"라고 되물음
- 보안 구조 설명에서 틀린 말이 한 번 나오면 그 업체 자료를 처음부터 다시 봄

### 13.2 시청 안에서

- 보고는 짧게. 한 장에 경로 그림 하나와 결론 세 줄
- 팀원에게는 지시보다 질문으로 시작함. "이거 어디로 나가는 것 같아?"
- 외주 인력에게도 존댓말. 다만 보안 서약 위반에는 예외 없이 계정을 막음

### 13.3 배선영 주무관과의 관계

- 2024년 초 보안 솔루션 구매를 메신저 두 줄로 요청했다가 "계약 의뢰서 양식으로 다시 주세요"라는 회신을 받음. 그 뒤로는 선영에게 갈 때 근거 조항과 금액을 먼저 적어 감
- 선영이 기술을 모르는 걸 부끄러워하지 않고 그 자리에서 묻는 점을 좋게 봄. 재석도 "제가 계약은 모릅니다"라고 편하게 말함
- 선영이 "그래서 결론은요?"라고 물으면 재석은 웃으면서 결론을 한 번 더 말함
- 재석이 급하게 일을 밀어붙이면 선영이 "급한 건 보안 사정이고 계약은 절차대로"라고 선을 그음. 재석은 그 선 덕분에 2025년 감사에서 지적이 없었다는 걸 앎
- 다른 팀장들에게 "배 주무관 통과하면 감사도 통과한다"고 말함

### 13.4 자주 하는 말

- "그거 어디로 나갑니까?"
- "망 넘어가는 건 안 됩니다."
- "로그 남습니까?"
- "원칙은 원칙이고요."
- "제가 직접 해 보겠습니다."
- "보류지 거절은 아닙니다."

## 14. 반대로 돌아설 수 있는 사유

- 설치나 라이선스 인증에 인터넷 연결이 필요하다는 사실이 드러나는 경우
- AI 분석을 위해 소스코드를 업체 서버나 외부 AI 제공사로 보내야만 하는 경우
- 웹 서비스가 envelope을 열 수 있거나, 실행기가 웹 서비스가 보낸 해시를 믿는 등 보안 설명과 실제 동작이 다른 경우
- 암호모듈 교체 계획을 묻는 질문에 일정 없이 "검토하겠다"만 반복하는 경우
- 외주 인력과 공무원을 구분할 방법이 없고, 그럴 계획도 없는 경우
- 감사 로그를 시 통합 로그 관리로 보낼 방법이 없는 경우

## 15. 사용 시나리오

### 시나리오 1: 명세 검토 (2026. 10. 29.(목) 밤)

1. 시연 다음 날 집에서 API 명세를 끝까지 읽음
2. 2.4절에서 Ed25519·HPKE를 보고 승원과 함께 검증대상 알고리즘 목록을 다시 찾아봄
3. 1.1절 Tailscale 문구에 빨간 줄을 긋고 "행정망 불가, 대체 구간 필요"라고 적음
4. 5.1절 검증 순서는 "이건 그대로 가져가고 싶다"고 적음
5. 다음 날 아침 질문 14개를 정리해 배선영 주무관에게 넘김. 공문 질의서에 들어갈 것

### 시나리오 2: 외주 패치 반영 (도입 후 상상)

1. 외주 개발자 류승현이 인터넷망 PC에서 만든 패치를 망간 자료전송시스템으로 반입함
2. 반입된 패치로 요청을 만들면 Plan의 작업은 CODE_FEATURE(MEDIUM)와 DEPLOY(HIGH) 두 개
3. 승인 기준표상 DEPLOY는 프로젝트 담당자(탁지훈, 추가 지정된 공무원 1명) 중 1명의 서명이 필요
4. 탁지훈이 행정망 PC에서 `approval-context`로 Plan 원문을 보고 서명함
5. 실행기가 해시와 서명을 검증하고 반영. 감사 로그에 승인자, 시각, IP가 남음

### 시나리오 3: 일부러 깨 보기 (시험 환경)

1. 석기원 주무관과 함께 웹 서비스 DB에서 Plan의 쿼리 한 줄을 바꿔 실행 요청을 보냄
2. 실행기가 `PLAN_HASH_MISMATCH`로 거부하고 경보가 옴
3. 외주 계정으로 승인을 시도하면 `403 NOT_APPROVER`가 나오는지 봄. 현재 명세로는 승인 기준표가 `ANYONE`이면 외주 계정도 승인될 수 있음을 확인함
4. 이 결과를 "승인권자 공무원 한정 필수"의 근거로 보고서에 붙임

### 시나리오 4: 외주 사업 종료일

1. 2028. 12. 31. 통합유지보수 사업 종료. 외주 인력 40명 중 요청자 계정 28개, 등록된 키는 0개(승인권 없음)여야 정상
2. 재석은 키 목록(`GET /admin/signing-keys`)에서 외주 인력 키가 하나도 없는지 먼저 확인함
3. 계정 비활성화는 한 명씩 `PATCH /admin/users/{userId}`로 해야 함. 사업자 단위 일괄 처리가 있으면 좋겠다고 메모함

### 시나리오 5: 보안성 검토 회의

1. 재석이 추진한 제품이라 검토자는 석기원 주무관과 외부 자문위원 1명으로 함
2. 검토 항목: 암호모듈, 망 구성, 인증 방식, 개인정보 처리, 로그 보관, 외주 인력 접근 범위
3. 현 명세 기준 "암호모듈 부적합, 망 구성 부적합(Tailscale), 인증 방식 보완 필요"로 나올 것을 재석은 이미 예상함

## 17. 한 줄 요약

노재석은 **구조는 인정하지만 기준은 양보하지 않는** 정보보안 팀장입니다. 실행기가 서명을 검증해야만 반영되는 설계를 그대로 두고, 암호모듈·망 구성·인증 방식을 시 기준에 맞출 계획을 일정과 함께 보여 주면 시청 안에서 도입을 가장 끈질기게 밀어붙이는 사람이 됩니다.
