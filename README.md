\# BeforeAI 고객 페르소나 검증 자료

BeforeAI(AI가 만든 작업 Plan을 승인자가 서명해야만 사내 실행기가 실행하는 서비스)를 실제 조직이 도입한다면 무엇을 보고, 무엇 때문에 망설이고, 무엇을 요구할지 가정해 본 자료입니다.
기준 명세는 BeforeAI-BE 저장소의 `.docs/named_api.md`이고, 문서 안의 "명세 2.3"과 같은 표기는 그 문서의 절 번호입니다.
각 문서에 적힌 `../named_api.md`, `../../named_api.md` 경로는 이 자료가 BeforeAI-BE 저장소의 `.docs/personas/`에 있던 때의 상대 경로입니다.

> 모든 조직, 인물, 금액, 사고, 법령 한도는 설계용 가정입니다. 실제 회사나 기관과 관계없습니다.

### 4.3 Tailscale 관련 지적에 대한 주의

명세(1.1, 5장)의 Tailscale은 **개발 단계에서 임시로 쓰는 내부망**이고, 운영 환경의 고정 요구 사항이 아닙니다. 페르소나들은 명세에 적힌 대로 Tailscale이 필수라고 보고 반응했기 때문에, 아래 지적은 "제품의 한계"가 아니라 "**운영 배포 구성이 명세에 없다**"는 문제로 읽어야 합니다.

| 조직 | 페르소나의 지적 | 다시 읽은 의미 |
| --- | --- | --- |
| 중소 | Tailscale을 켜면 재택에서도 내부망으로 판별되어 외부망 제한이 사라짐 | 내부망으로 볼 대역을 조직이 정할 수 있어야 함 |
| 중견 | Tailscale을 쓰지 않아 보안 심의를 새로 받아야 함. SSL VPN 접속이 내부망으로 판별되는지 불명 | 회사 VPN 대역을 내부망으로 등록할 수 있어야 함 |
| 정부기관 | 망분리 환경에서 Tailscale 불가, 행정망 내부 설치 필요 | 웹 서비스와 실행기를 기관 내부망에 두고 mTLS만으로 연결하는 구성이 필요 |
| 다국적 | Tailscale은 표준 도구가 아니라 예외 승인 필요, ZTNA 공용 IP 문제 | 사무소별 대역 등록과 ZTNA 환경 가이드가 필요 |

이렇게 보면 Tailscale 관련 지적은 5장의 **내부망 판별 대역 설정**과 **내부 설치형(인터넷 없이 동작)** 두 기능으로 모입니다. 이후 `../named_api.md` 1.1과 5장에 운영 구성을 "고객사 내부망 + 웹 서비스↔실행기 mTLS, 내부망 대역은 관리자가 설정, Tailscale은 개발 단계 임시"로 반영했습니다. 페르소나·회의록·공문은 반영 전 명세를 보고 쓴 기록입니다. 이 구성이면 중견기업의 보안 심의 지연과 다국적 기업의 Tailscale 예외 승인은 착수 조건에서 빠집니다. 정부기관의 보류 사유 중 행정망 설치 문제도 줄어들지만, KCMVP 암호모듈과 제품 인증 문제는 그대로 남습니다.

### 5.1 우선순위 (요청 빈도와 필수 지정 기준)

1. **감사 로그 내보내기**: 6곳 전부, 대부분 필수
2. **AI 분석 데이터 흐름 공개와 외부 전송 통제**: 6곳 전부. 기능이라기보다 문서와 설정 하나
3. **퇴사·계약 종료 일괄 처리**: 5곳
4. **승인 자격 구분 + 조회 전용 역할**: 4곳. 역할 모델 확장 하나로 함께 해결 가능
5. **내부망 판별 대역 설정**: 5곳. Tailscale이 개발용 임시 구성이므로(4.3) 운영 배포 전에 반드시 필요
6. **변경된 작업만 재승인, 대리 승인, 처리 시간 통계**: 승인 피로를 줄이는 기능. 기술 담당자 전원이 걱정

## 6. 해커톤에서 좋은 성적을 얻기 위해 있으면 좋은 기능

> 이 장은 위 결과를 바탕으로 한 제안입니다. 심사 기준은 일반적인 해커톤 기준(문제 정의, 완성도, 시연 효과, 기술적 새로움, 실현 가능성)을 가정했습니다.

### 6.1 고른 기준

- 페르소나 여러 명이 **직접 시험해 보겠다고 한 것** (6곳 모두 회의록에 변조·재전송 시험이 있음)
- **3~5분 시연 안에 눈으로 보이는 것**
- 다른 AI 코딩 도구나 결재 시스템에 **없는 것**
- 현재 명세 구조(해시, 서명, 실행기 검증) 위에 **며칠 안에 얹을 수 있는 것**

### 6.2 꼭 보여 줄 기능 (핵심 5개)

| 순위 | 기능 | 무엇을 보여 주나 | 근거 | 구현 범위 |
| --- | --- | --- | --- | --- |
| 1 | **공격 시연 모드 (Red Team 버튼)** | 화면에서 버튼으로 "DB에서 Plan 바꿔치기", "승인 envelope 재전송", "폐기된 키로 서명", "외부망에서 배포 승인"을 실행. 실행기가 `PLAN_HASH_MISMATCH`, `NONCE_ALREADY_USED`, `KEY_NOT_REGISTERED`, `INTERNAL_NETWORK_ONLY`로 막는 장면과 경보를 실시간으로 표시 | 6곳 모두 시범 시험 항목. 정우진 페르소나는 이 결과를 CTO 보고서 첫 장에 넣음 | 이미 있는 5.1 검증을 호출하는 데모 API와 화면 |
| 2 | **승인 화면의 쉬운 말 요약과 영향 범위** | 승인 버튼 위에 "이 작업은 `orders` 테이블 312행의 `status`를 바꿉니다. 운영 DB, 되돌릴 수 없음"처럼 한 줄 요약. DB 작업은 실행 전 dry-run(`EXPLAIN`, `SELECT COUNT(*)`)으로 영향 행 수 계산 | 한성(아내 UX 디자이너의 지적), 중소(312건 사고) | `approval-context`에 `summary`, `impact` 필드. AI 요약은 해시 대상에서 제외 |
| 3 | **실행 증명서 (Proof of Approval)** | 요청 하나를 골라 "누가, 언제, 어느 망에서, 어떤 해시에 서명했고, 실행기가 무엇을 검증했는지"를 한 장짜리 PDF·CSV로 내려받기. 구매·감사 담당이 그대로 감사에 제출 가능 | 감사 로그 내보내기가 6곳 전부의 필수 조건. 비기술 담당 6명 모두 "보고서에 옮길 숫자와 문장"을 원함 | `GET /requests/{id}/proof`, `GET /audit-logs/export` |
| 4 | **위변조가 드러나는 감사 로그 (해시 체인)** | 감사 로그 각 행이 이전 행의 해시를 포함. DB에서 로그 한 줄을 고치면 `GET /audit-logs/integrity`가 끊어진 위치를 빨간색으로 표시 | 정부기관 필수 요청. 1번 시연과 이어서 "로그도 못 지운다"까지 보여 줄 수 있음 | 감사 로그 테이블에 `prev_hash`, `hash` 컬럼과 검증 API |
| 5 | **작업 단위 해시로 바뀐 작업만 재승인** | Plan 해시를 작업별 해시를 묶은 머클 루트로 만들고, 서명은 작업별 해시 목록에 함. Plan에서 작업 하나를 고치면 그 작업의 서명만 무효, 나머지 서명은 유지되는 장면 | 5곳이 걱정한 승인 피로. 보안을 유지하면서 불편을 줄이는 설계라 기술 심사에서 설명하기 좋음 | 2.3 해시 구조 변경. 실행기 검증 순서 2·3단계 수정 |

### 6.3 시간이 남으면 추가할 기능

| 기능 | 효과 | 근거 |
| --- | --- | --- |
| 원클릭 퇴사 처리 | 계정 비활성화, 키 폐기, 승인 대기 요청 `REAPPROVAL_REQUIRED` 전환을 한 번에. 이어서 "퇴사 전에 받아 둔 서명으로 실행 시도 → 거부"까지 시연 | 5곳 요청. 중견기업 필수 조건 1번 |
| 승인 자격 정책 (학생·협력사·외주 모드) | 계정에 `approvalEligible: false`를 주면 실행기에서도 `APPROVER_NOT_ELIGIBLE`로 거부 | 고등학교, 중견, 정부 |
| 실행 시간 창과 변경 티켓 | 해시 대상에 `executionWindow`와 티켓 번호를 넣고, 창을 벗어나면 실행기가 거부 | 다국적 기업 필수 요청. "승인했지만 지금은 안 됨"이라는 새 장면 |
| DB 작업 자동 백업 작업 | `DATA_WRITE`·`DB` 작업 앞에 대상 행 백업 작업을 자동으로 넣어 킬 스위치 후 복구 가능 | 중소, 중견. 현재 명세의 롤백 한계(3.7)를 메움 |
| 승인 피로 대시보드 | 승인 대기 시간 중앙값, 사람별 승인 쏠림 비율(예: CTO 50% 초과 경고) | 중소기업 통과 기준(CTO 승인 50% 이하), 한성 "5분 규칙" |
| 비개발자용 월간 보고 문장 | "이번 달 고위험 작업 12건, 모두 담당자 서명 후 실행, 승인 없는 실행 0건" | 김미경, 노현숙, 노상규의 시나리오 |

### 6.4 해커톤에서 하지 않는 것이 좋은 것

- **SSO·SCIM, KCMVP 암호모듈, 실행기 이중화**: 요구는 분명하지만 시연에서 보이지 않고 시간이 많이 듭니다. 발표 자료의 "로드맵"이나 "설계상 교체 가능한 구조"로만 언급하는 편이 낫습니다.
- **Slack 외 알림 여러 개**: 웹훅 하나만 만들면 메일·메신저는 같은 구조라고 설명할 수 있습니다.

### 6.5 5분 시연 흐름 예시

1. **문제 (30초)**: "AI가 만든 쿼리가 주문 312건을 바꿨습니다." 6개 조직의 사고 표(2장)를 한 장으로 보여 줌
2. **정상 흐름 (1분)**: 프롬프트 제출 → Plan과 쉬운 말 요약(6.2-2) → 담당자 서명 → 실행
3. **공격 (1분 30초)**: Red Team 버튼(6.2-1)으로 Plan 변조, 서명 재전송, 외부망 배포 승인. 모두 실행기에서 차단되고 경보가 뜸
4. **감사 (1분)**: 감사 로그 한 줄을 DB에서 고치면 무결성 검사가 실패(6.2-4). 실행 증명서를 내려받아 보여 줌(6.2-3)
5. **편의 (30초)**: 작업 하나만 고쳤을 때 그 작업만 재승인(6.2-5)
6. **검증 근거 (30초)**: "6개 유형 조직 페르소나 검토에서 공통 필수 조건이던 기능을 구현했다"는 5장 표 한 장

## 7. 문서별 참고 사항

- 정부기관 회의록에서 배선영의 일곱 번째 발언은 셸 처리 문제로 API 경로 두 개가 빠진 채 Codex에 전달되었습니다. 회의록 머리말에 적어 두었습니다.
- 중견기업 회의록의 Codex 응답은 마지막 턴만 원본 파일과 대조했고, 앞선 턴은 도구 출력에서 옮겨 적었습니다.
- 고등학교 회의록에서 구은하의 마지막 보충에 대한 노상규의 답은 Codex에 보내지 않았고, 회의록 2.10에 "작성자가 회의 직후 반영"이라고 적었습니다.
- 공문에 적힌 API 경로 중 명세에 없는 것은 모두 조직 쪽의 제안 형태이며, 실제 설계는 따로 정해야 합니다.
